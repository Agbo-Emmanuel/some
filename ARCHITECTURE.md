## 0. Reading Guide & Confidence Legend

This codebase is **frontend-only**. The Python/Node backend that implements `/api/v1/*`
is **not in this repository**. Consequently, this document distinguishes three confidence tiers:

| Tier | Meaning | How to treat it |
|------|---------|-----------------|
| ✅ **Verified** | Read directly from source in this repo. Exact identifiers, line references given. | Safe to rely on. |
| ⚠️ **Inferred** | Reconstructed from the endpoint catalogue, service signatures, and consumer code. The contract is *implied* by how the frontend calls it. | Verify against the backend before depending on exact field names. |
| 🔴 **Stale / Broken** | The code demonstrably does something other than what it appears to. Documented as-is, with the actual behaviour. | Fix before building on it. |

### Two facts that change how you read everything else

1. **There is no event broker, message queue, or pub/sub bus in this codebase.**
   The phrase "event system" in this document refers to a **layered event model** that I
   define precisely in [Section 5](#5-event-system-documentation). The two genuine
   cross-cutting event pipelines in the codebase are the **axios interceptor chain**
   (transport-level events) and the **React state/DOM event layer**. Domain events
   ("the user registered", "a document was generated") exist as **API calls**, not as
   messages.
2. **Most of the dashboard is not wired to the backend.**
   Only `src/landing/auth/*` (Signup, Login, Otp, Onboarding) actually calls the API.
   Every other dashboard page simulates persistence with `setTimeout`. This is the
   single most important fact for an AI agent: **the service layer is the contract,
   the UI is largely a mock.** See [Section 16](#16-known-limitations).

## 1. System Overview

### 1.1 What the system does

**Ahiia.AI** is a web application that lets a small-business owner generate professional
business documents (proposals, contracts, SOPs, pitch decks, marketing plans, business
plans) by answering a short, structured questionnaire. The application captures the
user's business context once (company profile, brand kit, AI-drafted mission/vision/
advantage/audience) and reuses it to personalise every document it generates.

### 1.2 Business purpose

Small and medium businesses repeatedly write the same kinds of documents — a client
proposal, a service contract, a standard operating procedure — and every one of them
re-invents tone, structure, and boilerplate. Ahiia's proposition is:

> *Capture the business's knowledge once; generate consistent, on-brand documents forever.*

The product moat is **the company profile + brand kit context**, not the text generation
itself. Every UI surface reinforces this: the "Company Profile" and "Brand Kit" cards
appear on the setup page, the overview page, and the generation modal summary.

### 1.3 Core responsibilities

|---|---|---|

| Authentication (email+password, OTP verification, password reset) | `src/landing/auth/**` | ✅ Real (calls API) |

### 1.4 Key workflows

```
W1  Signup → OTP verify → Login → Onboarding → Dashboard
W2  Login (existing user) → Dashboard
W3  Create Document → pick template → fill required sections → review modal → generate
W4  Forgot password → email link → reset (NOT IMPLEMENTED end-to-end)
W5  Onboarding (6 steps): Welcome → Business Details → Business Context →
    AI Profile Review → Brand Kit → Done
W6  Document listing, filtering, sorting (client-side over a mock array)
```

### 1.5 Target users

| Persona | Entry point | Needs |
|---|---|---|
| Prospective customer | `/` | Understand value, join waitlist |
| New user | `/signup` | Create account, verify email, onboard |
| Returning user | `/login` | Get back to their documents fast |
| Admin / platform operator | `/admin` | Monitor users, verifications, AI usage, system health |

The product is clearly aimed at **Nigerian/SME operators** — hardcoded company
"SolarTech Nigeria", `₦` (naira) currency prefixes on money inputs, and an onboarding
industry list skewed to local business sectors.

### 1.6 Major architectural principles

1. **Thin client, fat server.** The frontend owns presentation and form state; the
   server owns identity, persistence, and AI generation. The service layer
   (`src/services/**`) is the only sanctioned way to talk to the server.
2. **Config-driven document templates.** `src/config/documentTemplates.js` is the single
   source of truth for what a document type is, what its required sections are, and how
   completion is judged. Adding a document type is a config + form + registry change —
   not a page change.
3. **Progressive disclosure wizard.** Onboarding is a 6-step wizard that defers all
   persistence to explicit "Continue" actions rather than autosaving.
4. **Reusable chrome.** `DashboardLanding` + `SideBar` + `DashboardHeader` are shared
   verbatim between the user and admin dashboards; only the nav-item arrays differ.
5. **Design-system-by-copy.** There is no component library; there is a family of
   hand-written Tailwind class strings repeated across files. Consistency is a
   convention, not a guarantee.

The code reads as a **high-fidelity design prototype that grew a real API layer**.

The frontend was designed first (beautiful, complete-looking screens) and the backend
was integrated later, into the auth/onboarding seam. The document-generation seam was

### 1.8 Why does this system exist? What problem does it solve?

It exists to remove the blank-page tax from writing routine business documents.
A founder with a real business but no writer today either (a) pays for a template and
loses consistency, (b) hires someone, or (c) writes everything from scratch. Ahiia
productises option (c) into a repeatable pipeline: capture context once, answer a
targeted questionnaire per document type, and get a structured first draft.

### 1.9 The three concepts a developer must understand first

1. **The service layer is the contract; the UI is a mock.** `src/api/endpoints.js` +
   `src/services/**` define what the backend can do. Only `src/landing/auth/**` uses
   them. Wiring the rest of the dashboard is the main outstanding engineering work.
2. **The template registry is a two-key join.** A document type is identified by
   `templateId` (e.g. `"business-proposal"`). That id must exist in **three** places:
   `TEMPLATES` (config), `FORM_REGISTRY` (registry), and the URL. Completion is
   computed by a **per-form exported `getCompletedSections(data)` function**, not by the
   config. See [§14.1](#145-document-type-catalogue).
3. **Auth is cookie-based with a silent-refresh interceptor.** Access and refresh tokens
   live in **non-HttpOnly cookies** read by `src/api/api.js`. Every request automatically
   carries `Authorization: Bearer <accessToken>`. A `401` with
   `detail === "Invalid or expired token"` triggers a refresh + retry **exactly once**.

## 2. Architecture Overview

### 2.1 Architectural style

**Single-page application, layered "smart component + service" architecture.**

- Not MVC, not Flux/Redux, not micro-frontends, not server-rendered.
- React 19 function components with **local `useState`** as the only state primitive.
  There is **no global store** — no Redux, no Zustand, no Context provider for app
  state (the only provider is `CookiesProvider` from `react-cookie`).
- Routing is **declarative and centralised** in `src/App.jsx` using
  `react-router-dom` v7 `<BrowserRouter>` with nested routes and `<Outlet>`.
- Server communication is a **thin axios wrapper** with a request interceptor
  (attach bearer token) and a response interceptor (refresh-and-retry).

### 2.2 Layer boundaries

```
┌──────────────────────────────────────────────────────────────────────────┐
│  L4  PRESENTATION / ROUTING          src/App.jsx, src/landing/**,         │
│                                     src/dashboard/**                     │
│  - Route elements, layout shells (DashboardLanding, Landing)             │
│  - Feature pages (Overview, Documents, BrandKit, Onboarding…)           │
│  - Presentational components (SideBar, DashboardHeader, forms)           │
│  - Local component state (useState/useEffect/useMemo/useRef)             │
├──────────────────────────────────────────────────────────────────────────┤

│                                     src/dashboard/components/document-  │
│                                       setup/FormRegistery.js             │
│  - TEMPLATES catalogue, WRITING_STYLES, COMPANY_PROFILE placeholder     │
│  - FORM_REGISTRY: templateId → { Form, getCompletedSections }           │
│  - **No service imports allowed in this layer** (currently satisfied)    │
├──────────────────────────────────────────────────────────────────────────┤
│  L2  SERVICE / DATA ACCESS            src/services/*.service.js          │

│                                     src/api/endpoints.js (path catalogue)│
│  - baseURL from config, 60 s timeout                                   │
│  - request interceptor: attach Authorization                            │
│  - response interceptor: 401 → refresh → retry → logout redirect        │
├──────────────────────────────────────────────────────────────────────────┤
│  L0  CONFIG                          src/config/apiConfig.js            │
│                                     import.meta.env (VITE_*)             │

         │  third-party, out-of-band
```

**Enforced boundaries (by convention, not by tooling):**

| Rule | Enforced? | Notes |
|---|---|---|
| L4 may import L3/L2/L1 | ✅ | Normal |
| L2 may import L1 only | ✅ | Every service imports exactly `api` + `ENDPOINTS` |
| L1 may import L2 | 🔴 **Violation** | `api/api.js` imports `refreshToken` from `services/auth.service` — a **circular dependency** (see [§9.3](#93-the-circular-import-between-api-and-services)). |
| L3 must not import L2 | ✅ | `documentTemplates.js` and `FormRegistery.js` import no services. |
| L0 must not import anything else | ✅ | `apiConfig.js` imports nothing. |

### 2.4 Service boundaries and domain boundaries

**Domain boundaries** are represented purely by *service module* boundaries — there is
no DDD layer, no entity/DTO layer, no mappers.

| Domain | Service module | Endpoints owned |
|---|---|---|
| Identity | `auth.service.js` | `/api/v1/auth/*`, `/api/v1/admin/register` |
| Account | `user.service.js` | `/api/v1/user/me`, `/api/v1/user/notification-preferences` |
| Company profile | `profile.service.js` | `/api/v1/profile*` |
| Brand | `brandKit.service.js` | `/api/v1/brand-kit` |
| Documents | `document.service.js` | `/api/v1/documents*`, `/api/v1/document-drafts*`, `/api/v1/blueprints*` |
| Insights | `insights.service.js` | `/api/v1/dashboard`, `/api/v1/analytics/summary` |
| Public | `public.service.js` | `/api/v1/public/*` |
| Admin | `admin.service.js` | `/api/v1/admin/*` |

**Service-boundary rules:**
- Every service function is `async` and returns `response.data` (the parsed body),
  **not** the axios response. Callers therefore cannot access `status` or `headers`
  unless they change the service. This is why `api.js` had to double-unwrap
  (`response.data.access_token`) — a symptom of this rule ([§11.4](#114-token-contract-fragility)).
- Services are **stateless and side-effect-free at the transport layer** (except that
  `auth.service.logout` performs a hard `window.location.href` redirect).
- `src/services/index.js` re-exports every service module, but **nothing imports the
  barrel** — every consumer imports the concrete module. The barrel is dead code
  that also masks the `api ↔ auth.service` cycle.

**How components communicate:**

| Mechanism | Used for | Example |
|---|---|---|
| **Props (data down)** | Parent → child configuration | `DocumentSetup` → `<Form data={formData} onField={handleField} />` |
| **Callbacks (events up)** | Child → parent side effects | `onField("clientName", value)` → `setFormData` |
| **`useNavigate` / `<Link>`** | Route transitions | `navigate("/dashboard/documents")` |
| **`<Outlet context>`** | Parent → descendant, across route boundaries | `DashboardLanding` passes `setHeaderTitle`; `SettingsLanding` passes `{markDirty, registerSave}` |
| **React Context (`CookiesProvider`)** | Cross-tree cookie access | `useCookies([...])` in `Login`, `DashboardHeader` |
| **Cookies** | Cross-route, cross-reload persistence | `accessToken`, `refreshToken`, `userData` |
| **Axios interceptors** | Implicit, cross-cutting | bearer-token injection, token refresh, session termination |
| **Toasts** | Global, fire-and-forget notification | `toast.success("Logged in successfully")` |
| **Module-level constants** | Shared, mutable-by-convention singletons | `TEMPLATES`, `ENDPOINTS`, `FORM_REGISTRY` |

### 2.7 Why this architecture was chosen

- **Vite + React SPA** for fast iteration on a visually rich marketing site with no SEO
  requirement beyond the landing page (the landing page is currently a client-only
  SPA, which is a known SEO weakness).
- **Local state, no global store**, because the app has exactly one genuinely global
  concern (auth), and the codebase solves that with cookies + an HTTP interceptor
  rather than a store. This was the right call: it removes an entire class of
  boilerplate and the refresh-token dance lives in exactly one place.
- **Service layer** to keep the endpoint catalogue in one file and make the eventual
  backend swap a config change.
- **Config-driven templates** so that adding "Business Plan" required one config
  object + one form + one registry entry — visible in the git history as
  `updated the create document flow`.

### 2.8 Alternative designs intentionally avoided

| Alternative | Why not used |
|---|---|
| **Redux / Zustand / React Context for app state** | Avoided in favour of local state; the app's shared state (auth) is server-derived and short-lived. Downside now visible: profile/brand-kit data must be re-fetched per page and is not shared between pages. |
| **React Query / TanStack Query** | Not adopted. Consequence: no caching, no request deduplication, no automatic invalidation, and every page that needs data re-implements loading/error state by hand. `getUserProfile()` and `getBrandKit()` are called on every onboarding mount. |
| **Form library (React Hook Form / Formik)** | Not adopted; forms use raw `useState` + a single `formData` object per page. Consequence: `getCompletedSections` must re-implement validation as boolean expressions, which is exactly where the bugs in [§14.2](#142-the-completion-contract--the-single-most-important-rule-set) come from. |
| **Server-side routing / SSR (Next.js)** | Not adopted; Vercel is used purely as a static host with an SPA rewrite. |
| **Design system (shadcn / MUI / Radix)** | Not adopted; components are hand-rolled Tailwind. Consequence: duplicated class strings, no shared primitives, two icon libraries. |
| **WebSockets / SSE for live document generation** | Not adopted; generation is request/response. Consequence: no progress indication for real generation — `GenerateModal` has an `isGenerating` prop that is **never used** by the modal's markup. |
| **Central event bus (mitt / eventemitter3)** | Not adopted; cross-component communication is via props/callbacks/context. Consequence and rationale are documented in [§5.2](#52-why-there-is-no-event-bus). |

#### `src/api/api.js` — Axios instance + interceptors ★
- **Purpose:** The keystone transport module. Everything network-facing goes through it.
- **Public interface:** `api` (the configured axios instance).
- **Configuration:** `baseURL = BASE_URL`, `timeout: 60000` ("60s to handle Render
  cold starts" — the API is hosted on Render), `Content-Type: application/json`.
- **Request interceptor (lines 16–23):** reads `accessToken` from cookies and sets
  `config.headers.Authorization = "Bearer " + token`. **No token → no header**; the
  request proceeds unauthenticated rather than failing fast.
- **Response interceptor (lines 25–68):**
  - Trigger condition (all must hold): `error.response?.data?.detail === "Invalid or expired token"`
    **AND** `!originalRequest._retry`.
  - Action: call `refreshTokenApi({ refreshToken: cookies.get("refreshToken") })`,
    read `response.data.access_token`, write it back to the `accessToken` cookie,
    set the `Authorization` header on the original request, and **replay** it via
    `api(originalRequest)`.
  - Failure path: toast the server message (fallback `"Session expired. Please log in again."`),
    remove `accessToken`/`refreshToken`/`userData` cookies, hard-navigate to `/login`.
  - `_retry` is the infinite-loop guard: **each request can be retried at most once.**
- **⚠️ Import cycle:** `api.js` line 4 imports `refreshToken` from `services/auth.service`,
  which line 1 imports `api` from `api/api.js`. See [§9.3](#93-the-circular-import-between-api-and-services).
- **Should not contain:** business logic, component-specific error handling.

#### `src/api/endpoints.js` — Endpoint catalogue
- **Purpose:** Every backend path in one object. ~55 entries across 8 domains.
- **Conventions:**
  - Static paths are plain strings; parameterised paths are **arrow functions**
    (e.g. `DOCUMENT_BY_ID: (id) => \`/api/v1/documents/${id}\``).
  - Several endpoints have **backwards-compatible aliases** pointing at the same path:
    `VERIFY_OTP` ≡ `VERIFY_EMAIL`, `RESEND_OTP` ≡ `RESEND_VERIFICATION`.
  - Several constants are **duplicates of the same path** for readability
    (`DOCUMENTS` / `GET_DOCUMENTS` / `CREATE_DOCUMENT` are all `"/api/v1/documents"`).
- **Two unused constants:** `UPDATE_PROFILE_FIELD` (the service builds the path by
  string-concatenating `UPDATE_USER_PROFILE` instead) and `PROFILE_BUSINESS_CONTEXT`
  (the service uses it, but `updateBusinessContext` is itself never called).
- **Path collision hazard:** `UPDATE_PROFILE_FIELD: (field) => "/api/v1/profile/${field}"`
  and `PROFILE_BUSINESS_CONTEXT: "/api/v1/profile/business-context"` overlap. A
  `field` value of `"business-context"` would route to the business-context handler.

#### `src/config/apiConfig.js`

- **⚠️ The fallback host (`www.api.ahiia.ai`) differs from the `.env` host
  (`api.ahiia.ai`).** If `VITE_API_URL` is unset, the app talks to a different host
  than production. See [§10.3](#103-known-configuration-defects).

- **Purpose:** The only screens with real server integration (plus `Onboarding`).

#### `src/dashboard/userDashboard/settings/SettingsLanding.jsx` ★ (custom save protocol)
- **Purpose:** Settings layout with tab nav and a **single global Save button**.
- **Custom protocol:** the parent holds `dirty`, `saving`, `saved`, `saveHandler`.
  - `registerSave(fn)` → `setSaveHandler(() => fn)` (the `() => fn` wrapper is
    essential — otherwise React would call `fn` as a state updater).
  - `markDirty(value = true)` → `setDirty(value)`.
  - `handleSave()`: `if (!dirty || saving) return;` → `setSaving(true)` → `await saveHandler()`
    (or a 700 ms sleep if no child registered one) → `setSaving(false)` → `setDirty(false)`
    → `setSaved(true)` → clear `saved` after 2200 ms.
- **Children participate via `useOutletContext()`** → `{ markDirty, registerSave }`.
- **⚠️ Shadowing:** the nested `<Outlet>` here means settings tabs **cannot** access
  `DashboardLanding`'s `setHeaderTitle`.
- **⚠️ No unregistration:** when a tab unmounts, the parent keeps a stale handler
  until the next tab registers its own.
- **`SecuritySettings` never calls `markDirty()`** → the Save button stays permanently
  disabled on the Security tab.

#### `src/hooks/useScrollSpy.js` & `src/utils/scrollToSection.js`
- `useScrollSpy(ids, rootMargin="-45% 0px -45% 0px")` returns the id of the most
  visible element. Uses an `IntersectionObserver`; resolves `document.getElementById`
  **once at mount** — so it never re-evaluates on route change, and on `/about` or
  `/contact` (where the anchor ids don't exist) it stays stuck on `"product"`.
  The effect dep is `ids.join(",")` to tolerate the caller passing a new array each
  render.
- `scrollToSection(id)` scrolls to `document.getElementById(id)` minus the height of
  the **first `<header>` in the document** (which on dashboard pages is
  `DashboardHeader`'s, not the marketing header). Silently returns if the target is
  missing — which is why `#get-started` does nothing.

## 4. Application Lifecycle

### 4.1 Startup sequence

```
1.  Browser requests "/"  (or any path)
2.  Vercel rewrite rule: vercel.json → all paths serve /index.html   (SPA fallback)
3.  Browser parses index.html
      └─ <div id="root">, <script type="module" src="/src/main.jsx">
4.  main.jsx executes
      ├─ import "./index.css"  → Tailwind v4 compiles the utility layer
      ├─ createRoot(document.getElementById("root"))
      └─ render(<StrictMode><CookiesProvider defaultSetOptions={{path:"/"}}><App/></CookiesProvider></StrictMode>)
5.  App.jsx executes
      ├─ <BrowserRouter> mounts; it reads window.history and resolves the current URL
      ├─ <ScrollToTop/> mounts (useEffect → window.scrollTo(0,0))
      ├─ <ToastContainer/> mounts (global toast sink, portal to body)
      └─ <Routes> matches the current pathname → mounts the matching element
6.  The matched route element mounts
      ├─ If it is a layout route, the layout mounts first, then <Outlet/> resolves
      ├─ If it is DashboardLanding: SideBar + DashboardHeader render; the child
      │   route's component renders inside <main>
      └─ If it is Onboarding: useEffect (preload) fires →
            Promise.allSettled([getUserProfile(), getBrandKit()])
            → 2 GET requests, each carrying Authorization if a cookie exists
7.  React commits; effects run (twice in dev due to StrictMode)
```

### 4.2 Configuration loading

- **Build time:** Vite replaces `import.meta.env.VITE_*` literals at build time from
  the environment / `.env` files. There is **no runtime configuration** — changing
  `VITE_API_URL` requires a rebuild.
- **Read points (only two):**
  - `src/config/apiConfig.js` → `BASE_URL`.
  - `src/utils/cloudinary.js` → `VITE_CLOUDINARY_CLOUD_NAME`, `VITE_CLOUDINARY_UPLOAD_PRESET`.
- **`.env` values present in the working tree (git-ignored):**
  ```
  VITE_API_URL=https://api.ahiia.ai␠        ← note the trailing space
  VITE_CLOUDINARY_API_KEY=981886566623639
  VITE_CLOUDINARY_API_SECRET=xTIw6Lxk0RPZseb-UgM1b6uCkOU
  VITE_CLOUDINARY_CLOUD_NAME=ollgapjp
  VITE_CLOUDINARY_UPLOAD_PRESET=Ahiia.AI
  ```
- **The Cloudinary API key and secret are never used by the code** — only the cloud
  name and the unsigned upload preset are. The key/secret are pure exposure risk.

### 4.3 Dependency registration order

There is no DI container. "Registration" is just module import order:

```
main.jsx
 └─ App.jsx
     ├─ react-router-dom        (provides router context)
     ├─ react-toastify          (provides toast context)
     └─ landing/auth/*          (imports services → api → config/apiConfig)
```

Because ES modules are hoisted, `api/api.js` is fully evaluated before any component
renders. The axios instance and its interceptors are therefore **installed before the
first request can be issued** — which is correct.

**Circular import resolution:** `api/api.js` → `services/auth.service.js` → `api/api.js`.
ESM handles this by hoisting function declarations, so `refreshToken` is defined by the
time the interceptor body runs. **It works, but it is fragile**: if either module were
changed to use `const` at module scope for the same binding, or if the interceptor were
moved to module-evaluation time, it would break.

### 4.4 Service bootstrapping

There is no bootstrap step. The axios instance is created at module-evaluation time:

```js
export const api = axios.create({
  baseURL: BASE_URL,
  timeout: 60000,
  headers: { "Content-Type": "application/json" },
});
```

**Failure points at startup:**
| Failure | Symptom | Detection |
|---|---|---|
| `VITE_API_URL` missing | Falls back to `https://www.api.ahiia.ai` — a **different host** than production. Requests appear to hang/fail with CORS errors. | Network tab shows the wrong host. |
| `VITE_API_URL` has a trailing space | Base URL becomes `https://api.ahiia.ai␠` → axios joins to `https://api.ahiia.ai␠/api/v1/...`; the browser percent-encodes the space. Result: 404/400 from the API. | Network tab shows `%20` in the URL. |
| API cold start (Render free tier) | First request hangs up to ~60 s then times out. The 60 s timeout exists for this reason. | Spinner with no error toast; browser shows `ERR_NETWORK`/timeout. |
| CORS misconfiguration on the API | Every request fails preflight. | Console shows a CORS error; axios error has no `response`. |
| Cloudinary env missing | Logo upload throws `TypeError: Failed to fetch` (URL becomes `https://api.cloudinary.com/v1_1/undefined/image/upload`). | Onboarding step 2 logo upload fails silently (the `catch` only logs). |
| A route is missing from `App.jsx` | Blank content area (the layout still renders). | "Not Found" in the router, or `useOutletContext` returning `{}`. |

### 4.5 Runtime execution

```
User action (DOM event)
  → React synthetic event handler
  → setState (batched)
  → re-render of the owning component (and only its subtree)
  → useEffect/useMemo recompute as needed
  → if the action triggered a service call:
        service fn → api instance → request interceptor (attach bearer)
        → network → response interceptor (maybe refresh+retry)
        → response.data → setState → re-render
  → toast(...) for user feedback
```

**Render-order note:** `DocumentSetup` computes `completedKeys` in a `useMemo` keyed on
`[registryEntry, formData]`. Because `registryEntry` is a **stable object reference**
(from the module-level `FORM_REGISTRY`), the memo recomputes only when `formData`
changes — correct. But if `FORM_REGISTRY` were rebuilt per render, the memo would
recompute every render.

### 4.6 Shutdown

There is **no explicit shutdown** in a browser SPA. The relevant teardown paths:

| Path | What happens |
|---|---|
| **Logout (header)** | `removeCookie("accessToken")`, `removeCookie("refreshToken")`, `navigate("/login")`. **Server session is NOT revoked.** |
| **Logout (`auth.service.logout`)** | `POST /api/v1/auth/logout` then `finally` → optional `clearCookies()` → `window.location.href = "/login"` (full reload). **This function is never called from any component.** |
| **Refresh failure** | Response interceptor removes `accessToken`/`refreshToken`/`userData` and does `window.location.href = "/login"` (full reload). |
| **Unmount** | React runs effect cleanups: `useScrollSpy` disconnects its observer; `Header` removes its scroll listener; `Documents`/`DashboardHeader` remove their `mousedown` listeners; `Otp` clears its interval; `Analytics`/`BrandKit` clear their `setTimeout`s. |
| **Uncleaned `setTimeout`s** | `CompanyProfile`'s "Save Changes" (800 ms + 2200 ms) and "Regenerate" (1100 ms) are **not** cleared on unmount → React 19 will warn about setting state on an unmounted component. |

**⚠️ Deviation:** `DashboardHeader.handleLogout` does **not** call `auth.service.logout`,
so `POST /api/v1/auth/logout` never fires from the UI. The refresh token therefore
remains valid on the server until it expires.

## 5. Event System Documentation

> **Read this section first if you are an AI agent.** It is the highest-value part of
> this document.

### 5.1 What "event" means in this codebase

There is **no message broker, no event emitter library, no WebSocket, no SSE, and no
server-sent domain-event stream**. The application has no `mitt`, no `eventemitter3`,
no `EventTarget` subclass, and no `useEventBus` hook.

What it does have is a **six-tier event model**, where different tiers are used for
different purposes and have wildly different guarantees. Misunderstanding which tier a
given "event" lives in is the #1 source of incorrect reasoning about this codebase.

| Tier | Name | Mechanism | Async? | Ordered? | Durable? |
|---|---|---|---|---|---|
| **T1** | DOM / synthetic events | React's delegated event system | No | Per-dispatch | No |
| **T2** | Component state transitions | `useState` setters | No | Yes | No |
| **T3** | **Domain events** (the real business events) | Service function calls → HTTP | Yes | Yes (request order) | Server-side |
| **T4** | **Transport events** (cross-cutting) | Axios interceptors | Yes | Yes (per request) | No |
| **T5** | **Notification events** | `react-toastify` | Yes (animated) | No | No |
| **T6** | **Navigation events** | react-router | Yes | No | No |
| **T7** | **Remote events** (server-originated) | WebSocket/SSE — **not implemented** | — | — | — |

**The one genuine publish/subscribe channel in the app is T5 (toasts):** any module can
call `toast.success(...)` and the `<ToastContainer/>` at the app root renders it.
`ToastContainer` is the app's only long-lived subscriber that is decoupled from the
producer's tree. Everything else uses direct calls (T3) or direct coupling (T1/T2).

### 5.2 Why there is no event bus

**This is a deliberate architectural choice, not an oversight.** Reasoning:

1. **The event volume is tiny.** Roughly 12 distinct user-triggered business actions
   exist across the entire app. A pub/sub bus is justified at hundreds of producers or
   when events must cross process boundaries. Here, an `EventTarget` would add a layer
   of indirection over what is effectively `await service(); setState(); toast();`.
2. **Coupling is already explicit and readable.** `DocumentSetup` owns `formData`;
   the form components receive `onField` and call it. The dependency direction is
   obvious from the props.
3. **The problematic cross-cutting concern (auth) was solved with interceptors
   instead** — a middleware pattern that gives *better* guarantees than a bus
   (deterministic ordering, exactly-once retry via `_retry`) at a fraction of the cost.
4. **The consequences are real but bounded.** See [§5.9](#59-the-cost-of-not-having-a-bus).

If you ever add a bus, the three genuinely cross-cutting concerns that would benefit
are: **session invalidation**, **document-generation progress**, and
**cross-page cache invalidation** (e.g. "brand kit changed" → "document setup sidebar
must refresh"). Today all three are either stubbed or missing.

### 5.3 Tier 3 — Domain Event Catalogue (the core of the event system)

Each row is a **domain event**: a business-significant occurrence that the frontend
initiates. The "Event" column is the canonical name I assign for this document — it is
**not** present in the code, which identifies events only by endpoint path. Use these
names when reasoning about the system or proposing changes.

### 5.4 Tier 4 — Transport events (the cross-cutting pipeline)

The axios interceptor chain in `src/api/api.js` is the app's only **global,
cross-cutting, ordered** event pipeline. It is the piece of the codebase that most
behaves like a message bus, and it is the piece with the most subtle logic.

```
REQUEST
  │
  ├─▶ [R1] request interceptor
  │      read cookie "accessToken"
  │      if present → config.headers.Authorization = `Bearer ${token}`
  │      (absent → request proceeds unauthenticated; no error, no warning)
  │
  ├─▶ network  (baseURL + path, 60 s timeout, JSON content-type)
  │
  └─▶ [R2] response interceptor
         │
         ├─ success → pass through unchanged
         │
         └─ error:
            │
            ├─ NOT (detail === "Invalid or expired token")  → reject(error) unchanged
            │
            └─ detail === "Invalid or expired token" AND !originalRequest._retry:
                  │
                  ├─ set originalRequest._retry = true          ← exactly-once guard
                  ├─ [E1] auth.refresh event
                  │      POST /api/v1/auth/refresh  { refreshToken }
                  │      success → set cookie accessToken = body.data.access_token
                  │                replay originalRequest via api(originalRequest)
                  │                (the replay re-enters R1 and R2, but _retry is set
                  │                 so a second failure is NOT retried again)
                  │
                  └─ failure → [E2] session.terminated event
                         toast.error(message || "Session expired. Please log in again.")
                         remove cookies: accessToken, refreshToken, userData
                         window.location.href = "/login"     ← full page reload
                         reject(refreshError)
```

**Transport event definitions:**

| Event | Trigger | Consumers | Side effects | Failure behaviour |
|---|---|---|---|---|
| `request.authorized` | Every request with a token | The API | `Authorization` header set | None — a missing token is silent |
| `auth.expired` | 401 + `detail === "Invalid or expired token"` | The interceptor only | none | Any other 401 (e.g. `detail: "Not authenticated"`) is **not** handled → the user sees a raw error and stays on the page |
| `auth.refreshed` | Successful refresh | The original request (replayed) | new `accessToken` cookie | — |
| `session.terminated` | Failed refresh | The whole app | 3 cookies removed, hard redirect to `/login` | — |

**⚠️ The interceptor matches on an exact string.** `error.response?.data?.detail === "Invalid or expired token"`.
If the backend changes the wording, uses `message` instead of `detail`, or returns a
different status code, **the entire silent-refresh mechanism silently stops working**
and the app degrades to "every request 401s and the user is stuck". This single string
is a **load-bearing contract**. See [§18.4](#182-the-invariants--never-break-these).

**⚠️ `_retry` is stored on the axios config object**, which means the guard is
per-request-object, not per-endpoint. If the same config object were reused across
calls it would poison them — axios creates a fresh config per request, so this is
currently safe.

**⚠️ Concurrency:** if 5 requests 401 simultaneously, **5 refresh calls fire in
parallel**. Each will independently call `/auth/refresh` with the same refresh token.
If the backend rotates refresh tokens on use (single-use rotation), **all but one will
fail**, and the failure path wipes the cookies and redirects to `/login` — even though
the app is actually fine. This is the classic "refresh stampede" bug. It has not
manifested yet only because the dashboard makes few concurrent authenticated calls.
**When you wire the dashboard up, you must add refresh de-duplication.**

### 5.5 Tier 5 — Notification events

`react-toastify` is the app's only true publish/subscribe channel.

- **Publisher:** any module can `import { toast } from "react-toastify"` and call
  `toast.success/error/info/warning(...)`.
- **Subscriber:** the single `<ToastContainer />` mounted in `App.jsx` (sibling of
  `<BrowserRouter>`).
- **Delivery:** asynchronous (animation), auto-dismissed by default (default 5 s).
- **Ordering:** ⚠️ **Not guaranteed.** Toasts render in the order the container
  receives them, but concurrent calls (e.g. an interceptor toast racing a component
  toast) can interleave. Do not use toasts for sequencing.
- **Current publishers (complete list):**
  - `api.js` — `toast.error` on session expiry.
  - `Login.jsx` — `toast.success("Logged in successfully")`, `toast.error(...)`.
  - `Signup.jsx` — `toast.error("Passwords do not match")`, `toast.error("Please accept the terms and conditions")`, `toast.error(error.response?.data?.message || "Something went wrong")`.
  - `Otp.jsx` — `toast.success("OTP verified successfully")`, `toast.success("OTP resent successfully")` (unconditional — see [§5.3.1](#531-identity-domain-events)), `toast.error(...)`.
  - `Onboarding.jsx` — `toast.error("Please enter your business name")`, `toast.error("Some fields could not be saved. Please try again.")`.
- **Not used in:** every dashboard page. **No dashboard page emits a toast**, because
  no dashboard page calls a service.

### 5.9 The cost of not having a bus

| Consequence | Where it hurts |
|---|---|
| **No cache invalidation.** | Changing the brand kit in one place doesn't update `SetupSidebar`'s "Brand Kit connected" badge elsewhere. There is no cache to invalidate today only because there is no cache — and no data layer either. |
| **Duplicate fetches.** | `getUserProfile()` + `getBrandKit()` are called on every `Onboarding` mount. With StrictMode that's 4 requests in dev. |
| **Cross-page state drift.** | `Overview.jsx` shows "SolarTech Nigeria" hard-coded; `CompanyProfile.jsx` shows "SolarTech Nigeria" hard-coded; `BrandKit.jsx` has a module-level `const companyName = "SolarTech Nigeria"`. Change it in three places. |
| **Silent-failure windows.** | `setTimeout`-based "saves" and swallowed errors mean the UI can claim success while nothing was persisted (onboarding step 2 and step 5). |
| **No progress events.** | `GenerateModal` receives `isGenerating` and ignores it; real generation would need polling or a stream. |
| **No centralised error reporting.** | There is no `window.onerror` handler, no error-boundary, and no error-reporting service. A render error in any page blanks the whole app (see [§12.5](#125-render-errors)). |

### 5.10 Event dependencies, chains, and cascade risks

**Chains (strong ordering dependencies):**

```
profile.create ──▶ profile.aiComplete ──▶ profile.field.update × 4 ──▶ brandKit.update
   (needs companyName+industry)     (needs offer/audience)      (needs mission/vision…)      (needs colours/font)
```

**Cascade effects — what breaks if an upstream event fails:**

| If this fails | This cascades |
|---|---|
| `profile.create` | Step 3's AI profile is generated from a business the server may not have. `createAiProfile` may 404/422. |
| `profile.aiComplete` | `aiCards` are empty → step 4 shows 4 blank cards → **but the user can still Continue** (empty cards are skipped), and the profile is permanently without mission/vision. |
| `profile.field.update` | Step 4 blocks (the only blocking step). The user can hit "Skip AI profile" to escape. |
| `brandKit.update` | Step 6 still shows "Brand Palette" dots from local state → the user believes the palette was saved. |
| `auth.login` | No cookie → every later request goes out unauthenticated → silent 401s. |
| `auth.refresh` | **Session terminated** → full reload to `/login`. Any in-flight work is lost. |

**Circular dependency risks:**

1. **`api.js` ↔ `auth.service.js`** — a real ES-module cycle. Works today only because
   of function hoisting. **Risk:** refactoring `refreshToken` into a `const` arrow
   function, or moving interceptor registration to module scope, will produce a
   `ReferenceError` at runtime that no linter catches.
2. **Domain-level: none.** The domain event graph is a DAG (identity → profile →
   brand → documents → insights). No cycles.
3. **The `documentBrief` section key is shared** between `PitchDeckForm` and
   `BusinessPlanForm`. Not a runtime cycle, but a naming trap: if completion logic ever
   becomes key-global rather than per-template, the two will collide.

### 5.11 Failure handling summary for events

| Concern | Current state |
|---|---|
| **Retries** | Only the T4 token refresh retries the failed request — **exactly once** (`_retry`). No retry for network errors, 5xx, or timeouts. |
| **Dead-letter** | ❌ None. A failed domain event is either toasted, logged, or swallowed. `Promise.allSettled` in the onboarding preload and the step-2 fallback is the closest thing (it collects failures without surfacing them). |
| **Timeouts** | 60 s on the axios instance (for Render cold starts). Cloudinary upload uses raw `fetch` with **no timeout and no abort**. |
| **Duplicate handling** | ❌ No idempotency keys anywhere. Double-clicking a submit button fires the event twice. `Documents.jsx`'s "Create document" button has no in-flight guard. |
| **Idempotency** | Relies entirely on server-side semantics. `profile.create` has a **client-side mitigation** (the 400/409 → field-wise update fallback). |
| **Recovery** | Only the T4 path has a defined recovery (refresh → replay → or terminate → `/login`). Domain events have **no retry and no resume**. Onboarding state is **not persisted**, so a mid-flow failure means re-entering data. |
| **Ordering** | Within a component, `await`s are sequential. Across components, there is no ordering guarantee (concurrent `Promise.all` only in the onboarding preload). |
| **Cascade failure containment** | ❌ None. A single unhandled rejection (e.g. `Otp.jsx`'s unawaited `resendOtp`) becomes an unhandled promise rejection. |

## 6. Request and Data Flow

### 6.1 The universal request path

Every network call in this app follows exactly one shape:

```
Component
  │  (user intent)
  ▼
Service function  (src/services/*.service.js)
  │  await api.get/post/put/patch/delete(ENDPOINTS.X, payload)
  ▼
Axios instance  (src/api/api.js)
  │  [R1] request interceptor → attach Authorization: Bearer <accessToken>
  │  baseURL = BASE_URL, timeout = 60000, Content-Type: application/json
  ▼
Network (CORS, cross-origin — the browser talks to the API directly)
  │
  ▼
[R2] response interceptor
  │  success → pass through
  │  error + detail==="Invalid or expired token" + !_retry → refresh → replay
  ▼
Service returns response.data        ← the unwrapped body
  │
  ▼
Component setState(...) / toast(...) / navigate(...)
```

**Layers and their responsibilities:**

| Layer | File | Responsibility | Must NOT |
|---|---|---|---|
| Component | `src/**` | Owns UI state, calls a service, handles the result | Know the endpoint path |
| Service | `src/services/*.js` | Owns the endpoint path + method + payload shape | Touch state, toasts, navigation |
| Transport | `src/api/api.js` | Owns auth header, refresh, session termination | Know business meaning |
| Catalogue | `src/api/endpoints.js` | Owns every URL | Contain logic |
| Config | `src/config/apiConfig.js` | Owns the base URL | — |

### 6.2 Workflow: Login → dashboard (sequence)

```
User        Login.jsx        auth.service      api/api.js         Ahiia API       api/api.js
  │             │                 │                │                  │               │
  ├─submit─────>│                 │                │                  │               │
  │             ├─login({email,password})───────>│                  │               │
  │             │                 │                ├─[R1] cookie→Bearer│               │
  │             │                 │                ├──────POST /api/v1/auth/login────>│
  │             │                 │                │                  │               │
  │             │                 │                │<────200 {accessToken, refreshToken}─│
  │             │                 │                │                  │               │
  │             │                 │                │                  │               │
  │             │<────response.data────────────────│                  │               │
  │             ├─setCookie("accessToken", response.accessToken)────>│ cookie jar    │
```

### 6.3 Workflow: Onboarding step 2 (profile creation with fallback)

```
User clicks "Continue" (step 2)
  │
  ├─ GUARD: if (!companyName.trim()) → toast.error → RETURN (no request)
  │
  ├─ setLoading(true)
  ├─ await createUserProfile({companyName, industry, description, logoUrl})
  │      └─ POST /api/v1/profile
  │
  ├─ catch(err):
  │      if (err.response?.status === 400 || 409):
  │          await Promise.allSettled([
  │            updateUserProfile("companyName", "update", companyName),
  │            updateUserProfile("industry",    "update", industry),
  │            updateUserProfile("description", "update", description),
  │            ...(logoUrl ? [updateUserProfile("logoUrl","update",logoUrl)] : []),
  │          ])
  │          → each is PATCH /api/v1/profile/{field}  {action:"update", value}
  │          → ⚠ failures are SILENT (allSettled + unreachable catch)
  │      else:
  │          console.log(error)          ← ⚠ swallowed, no toast
  │
  └─ finally: setLoading(false); setStep(3)   ← ⚠ ALWAYS advances
```

**Validation performed:** `companyName` non-empty after trim. **Industry is optional.**
**Description is clipped to 240 chars in the input handler** (`setDescription(v.slice(0,240))`).

### 6.4 Workflow: Onboarding step 4 (AI profile persistence)

```
User clicks "Continue" (step 4)
  │
  ├─ anyError = false
  ├─ for (const card of aiCards):          ← SEQUENTIAL, one await at a time
  │      const fieldName = {mission:"mission", vision:"vision",
  │                         advantage:"competitiveAdvantage",
  │                         audience:"targetAudience"}[card.id]
  │      if (!fieldName || !card.content) continue        ← ⚠ empty cards skipped
  │      setSavingCards(prev => ({...prev, [card.id]: true}))
  │      try:
  │        await updateUserProfile(fieldName, card.action, card.content)
  │           └─ PATCH /api/v1/profile/{field}  {action, value}
  │             action ∈ {"Accept","Edit","Regenerate"}
  │      catch: console.log(...); anyError = true
  │      finally: setSavingCards(prev => ({...prev, [card.id]: false}))
  │
  ├─ if (anyError) → toast.error("Some fields could not be saved. Please try again.")
  │                 → STAY on step 4   ← the ONLY blocking step
  └─ else → setStep(5)
```

**⚠ `isAccepted` is not part of the condition.** Cards the user never accepted are
still persisted with `action: "Accept"`.

### 6.6 Workflow: Silent token refresh

See [§5.8 Example B](#example-b--silent-token-refresh-t4-deep-dive) for the annotated
sequence. Summary of the decision points:

| Condition | Action |
|---|---|
| `error.response` is undefined (network error, CORS, timeout) | Reject unchanged. **No refresh attempt.** |
| `error.response.data.detail !== "Invalid or expired token"` | Reject unchanged. **No refresh attempt.** |
| `detail` matches **and** `originalRequest._retry` is truthy | Reject unchanged (already retried once). |
| `detail` matches **and** `_retry` is falsy | Set `_retry = true`, refresh, replay. |

### 6.7 Failure paths at a glance

| Failure | Where handled | User sees |
|---|---|---|
| Network error / timeout | None | Axios error bubbles to the component's `catch` → toast (sometimes a raw `error.message`). |
| 400 validation | Component `catch` | `toast.error(error.response?.data?.message)` (Signup/Onboarding) or `error.message` (Login, Otp — raw axios text). |
| 401 with the magic detail | `api.js` interceptor | Silent refresh + retry, or session-termination toast + redirect. |
| 401 with any other detail | None | Rejected to the component → toast with a raw message. |
| 403 | None | Rejected to the component. |
| 404 / 409 / 5xx | Component `catch` | Varies; several paths swallow the error silently. |
| Cloudinary failure | `Onboarding.handleLogoUpload` catch | **Nothing** — `console.log` only; `logoUrl` stays `""`. |

## 7. State Management

### 7.1 There is no global state library

Confirmed absences: **no Redux, no Zustand, no MobX, no Jotai, no Recoil, no React
Context for application data, no SWR, no React Query.** The only React context in the
app is `CookiesProvider` (from `react-cookie`), which carries cookies, not app state.

### 7.2 Where state lives

| State | Location | Lifetime | Persisted? |
|---|---|---|---|
| `accessToken`, `refreshToken` | **Cookies** (path `/`) | Across reloads and tabs | ✅ Cookie jar (until the refresh failure wipes them) |
| `userData` | Cookie — **written by nobody, removed by the interceptor** | — | ⚠️ read-only in practice |
| Onboarding wizard state | `Onboarding.jsx` `useState` (18 vars) | Component lifetime | ❌ |
| Document setup form data | `DocumentSetup.jsx` `useState` | Component lifetime | ❌ |
| Settings form state | Each settings tab's `useState` | Tab lifetime | ❌ |
| Brand kit editor state | `BrandKit.jsx` `useState` | Page lifetime | ❌ |
| Company profile editor state | `CompanyProfile.jsx` `useState` | Page lifetime | ❌ |
| Documents list | Module-level `const DOCUMENTS` in `Documents.jsx` | **Forever** (module scope) | ❌ (but static) |
| Overview list | Module-level `const INITIAL_DOCUMENTS` in `Overview.jsx` | Forever | ❌ (but static) |
| Sidebar open state | `DashboardLanding.jsx` `useState` | Shell lifetime | ❌ |
| Header title override | `DashboardLanding.jsx` `useState` (`headerTitle`) | Shell lifetime | ❌ (never set) |
| Settings dirty/save protocol | `SettingsLanding.jsx` `useState` | Shell lifetime | ❌ |
| Toast queue | `react-toastify` internal | ~5 s per toast | ❌ |

### 7.3 State ownership rules

1. **A state variable has exactly one owner.** The owner is the component that calls
   its setter.
2. **Children never mutate parent state directly.** They call a callback prop
   (`onField`, `onChange`, `onSave`, `onGenerate`, `onReviewAndGenerate`).
3. **Cross-route data is passed via `location.state`** (ephemeral) or via cookies
   (auth only). There is no cross-route state store.
4. **Server state is not cached.** `getUserProfile()` is called on every onboarding
   mount; there is no reuse.

### 7.4 The `<Outlet context>` mechanism

This is the app's only cross-route communication channel, and it has a **shadowing
hazard**.

```
DashboardLanding
  └─ <Outlet context={{ setHeaderTitle }}>
       │
       ├─ Overview / Documents / … (children get {setHeaderTitle})
       │
       └─ SettingsLanding            ← renders its OWN <Outlet>
            └─ <Outlet context={{ markDirty, registerSave }}>
                 └─ AccountSettings / SecuritySettings / NotificationSettings
                    ↑ these get ONLY {markDirty, registerSave}
                    ↑ setHeaderTitle is SHADOWED and unavailable
```

**The save protocol (custom, undocumented outside this file):**

```js
// child
const { markDirty, registerSave } = useOutletContext();
useEffect(() => {
  registerSave(async () => { await persist(); });
}, [registerSave, /* deps */]);

// parent
const registerSave = useCallback((fn) => setSaveHandler(() => fn), []);
const markDirty = useCallback((v = true) => setDirty(v), []);
```

**Rules an agent must follow:**
- `registerSave` **must** be called with `setSaveHandler(() => fn)` semantics — the
  `() =>` wrapper prevents React from treating `fn` as a state updater.
- A child that changes state must call `markDirty()` or the parent's Save button stays
  disabled. **`SecuritySettings` violates this** → its Save button is permanently greyed.
- A child must **re-register** when its data changes, because the captured closure
  would otherwise hold stale values. `AccountSettings` and `NotificationSettings`
  include their data in the effect deps (churn on every keystroke, but correct).
- There is **no unregister** mechanism. A stale handler persists after a tab unmounts
  until another tab registers.

### 7.5 Caching

**There is no cache.** Not in memory (no memoised server-data store) and not on disk
(no `localStorage`, no `sessionStorage` — verified by grep across `src/`).

The only memoisation in the codebase is `useMemo` for **derived** values:
- `DocumentSetup`: `completedKeys` on `[registryEntry, formData]`.
- `Documents`: `types` (on `[]`) and `filtered` (on `[query, typeFilter, statusFilter, sortBy]`).
- `BrandKit`: `previewInitials` on `[companyName]` — where `companyName` is a module
  constant, so this memo is pointless.

### 7.6 Persistence strategy

| Data | Strategy | Status |
|---|---|---|
| Auth tokens | Cookie (`path: "/"`, **not HttpOnly**, **not Secure**, **not SameSite**) | ✅ Working |
| Everything else | **None** — reload loses it | 🔴 The central gap |

### 7.7 Eventual consistency considerations

The app is read-after-write on the server for profile and brand kit:
`Onboarding` writes the profile, then (on a later mount) reads it back. If the backend
is eventually consistent, the read-back may lag. There is no retry or
"waiting for consistency" logic.

**The one place this bites:** `Onboarding`'s mount effect calls `getUserProfile()` and
`getBrandKit()` in parallel. If a user finishes onboarding and immediately reloads
`/onboarding`, a lagging read would show stale values — and the user's next "Continue"
would **overwrite** the newer server state with the stale local state (because step 2
does a full `createUserProfile` with all four fields).

### 7.8 Concurrency concerns

| Concern | Status |
|---|---|
| Double-submit | ❌ Unprotected. `Login`, `Signup`, `Otp`, and `Onboarding` set `loading` and disable the button — but `Documents`' "Create document" and `Onboarding`'s "Accept all" have no guard, and `Onboarding`'s per-card `savingCards` allows concurrent card saves. |
| Concurrent requests | ✅ Rare. Only `Onboarding`'s preload uses `Promise.allSettled` (2 requests). |
| **Refresh stampede** | 🔴 **Real risk.** See [§5.4](#54-tier-4--transport-events-the-cross-cutting-pipeline). 5 parallel 401s → 5 parallel refresh calls. If the backend rotates refresh tokens, this logs the user out. Must be fixed before the dashboard is wired up. |
| Out-of-order state writes | ⚠️ `Onboarding` step 2's fallback fires **4 parallel** `PATCH /profile/{field}` calls. If two touch the same field, the last write wins — order is not guaranteed. |
| `setState` after unmount | ⚠️ `CompanyProfile`'s 800 ms / 2200 ms / 1100 ms timers are not cleared on unmount. React 19 no longer warns about this but the state update is simply lost. |

### 8.3 Relationships (⚠️ inferred)

- `User 1—1 CompanyProfile`, `User 1—1 BrandKit`, `User 1—1 NotificationPreference`.
- `User 1—N DocumentDraft`, `User 1—N Document`.
- `Document 1—N DocumentRevision` (linear history, `revert` points at a revision id).
- `Document 1—N DocumentGuidance` (each flag addressed by `flagId`).
- `Document 1—1 DocumentStyle`.
- `Document N—1 DocumentDraft` (a draft is promoted into a document on generation).
- `User 1—N GenerationLog` (feeds `admin.generations` and `admin.ai-usage`).

### 8.4 Why the schema is shaped this way (design rationale)

- **Profile is 1:1 with user, not a workspace/team entity.** The onboarding copy says
  *"Private workspace · Your business data stays within your workspace"* but there is
  no workspace/team/role-per-workspace concept — a user *is* a workspace. This is a
  deliberate simplification for a solo-founder product.
- **`industry` is a CSV string, not a relation.** The client sends
  `selectedIndustries.join(", ")` and the server returns a single string that the
  client splits on `","`. This is a pragmatic choice that avoids a join table, at the
  cost of fuzzy matching (see [§14.5](#1415-the-industry-csv-contract)).
- **Guidance flags are addressed by `flagId`, not by row id.** `PATCH /documents/{id}/guidance/{flagId}`
  suggests flags are a **stable, server-defined catalogue** (e.g. `missing-payment-schedule`)
  whose state lives per document. The marketing copy mentions *"Pricing section has no
  payment schedule"* — consistent with a fixed rule catalogue.
- **Revisions are a separate table, not a column.** `revert` and `regenerate-section`
  both need history, so revisions are first-class rows.

### 8.5 Critical constraints (⚠️ inferred from client behaviour)

| Constraint | Evidence |
|---|---|
| `description` ≤ 240 characters | The client clips with `.slice(0, 240)`. |
| `companyName` must be non-empty | The only hard client-side gate. |
| A profile's `industry` must be splittable on `","` | The client calls `.split(",")` on it. **An array response would crash the preload.** |
| `createUserProfile` returns 400 or 409 on a duplicate | The client's fallback branches on exactly those two codes. |
| `profile/{field}` accepts `mission`, `vision`, `competitiveAdvantage`, `targetAudience`, `companyName`, `industry`, `description`, `logoUrl` | The client PATCHes exactly these. |
| `profile/{field}` accepts an `action` verb | The client sends `Accept` / `Edit` / `Regenerate` / `update`. |
| `brand-kit` PUT accepts `primaryColor`, `secondaryColor`, `font`, `tagline` | The client sends exactly these four. |
| `POST /auth/refresh` returns an **enveloped** body `{data:{access_token}}` | The interceptor reads `response.data.access_token` after the service already unwrapped once. |
| `POST /auth/login` returns a **flat** body `{accessToken, refreshToken}` | `Login.jsx` reads `response.accessToken`. ⚠️ **These two cannot both be true** — see [§11.4](#114-token-contract-fragility). |
| A 401 body carries `detail === "Invalid or expired token"` | The interceptor's exact string match. |

### 8.6 Performance considerations

- **No pagination is implemented** client-side, though `getDocuments` accepts
  `{page, pageSize}`. The mock list has 7 items.
- **No request deduplication.** `getUserProfile()` and `getBrandKit()` are not cached;
  StrictMode doubles them in dev.
- **The 60 s timeout** is the dominant latency characteristic — a hung request blocks
  the UI for a full minute with only a spinner for feedback.
- **Cloudinary uploads bypass axios** → no timeout, no abort, no retry. A large SVG on
  a slow connection can hang the onboarding step indefinitely.

### 9.1 The Ahiia.AI API

### 9.3 The circular import between `api` and `services`

```
src/api/api.js
  ├─ import { BASE_URL } from "../config/apiConfig"        → no cycle
  ├─ import { toast } from "react-toastify"                 → no cycle
  └─ import { refreshToken as refreshTokenApi }
        from "../services/auth.service"                     ◄── CYCLE
              │
              └─ import { api } from "../api/api"            ◄── back to api.js
```

**Why it exists:** the interceptor needs to refresh the token, but `refreshToken` lives
in `auth.service`, which needs the axios instance. The natural fix is to inline the
refresh call in `api.js` (or to move it to a `refresh.service.js` that imports nothing
from `api.js`).

**Why it works today:** ESM hoists function declarations, so `refreshToken` is
initialised before the interceptor body ever runs (interceptors only execute on
requests, long after module evaluation).

**How it breaks:** if `refreshToken` were rewritten as `export const refreshToken = …`
**and** the interceptor were read at module-evaluation time, `api` would be
`undefined` at the moment `auth.service` evaluates. It would also break under
aggressive bundler tree-shaking or circular-dependency warnings becoming errors.

**⚠️ `src/services/index.js` makes this worse.** The barrel re-exports
`auth.service`, so anything importing the barrel pulls in the cycle. The barrel is
currently imported by nobody — **keep it that way** or delete it.

### 9.4 Google OAuth (planned, not implemented)

- `ENDPOINTS.GOOGLE_AUTH = "/api/v1/auth/google"` and `auth.service.googleAuth(payload)`
  exist.
- The "Continue with Google" buttons on `Login.jsx` and `Signup.jsx` have **no
  `onClick`**. The buttons are decorative.
- **Failure modes when implemented:** the payload shape is unknown (ID token vs

### 9.5 Vercel (hosting)

`vercel.json` contains exactly one rule:


## 11. Security Architecture

### 11.1 Authentication

**Mechanism:** email + password, with an email OTP verification step, and JWT access/
refresh token pairs stored in cookies.

```
signup ──▶ POST /auth/register ──▶ POST /auth/verify-email (OTP) ──▶ POST /auth/login
                                                                     │
                                        ┌────────────────────────────┘
                                        ▼
                            cookie: accessToken (JWT)
                            cookie: refreshToken (JWT)
                                        │
                                        ▼
                     every request: Authorization: Bearer <accessToken>
                                        │
                     401 + detail==="Invalid or expired token"
                                        ▼
                     POST /auth/refresh {refreshToken} ──▶ replay the request
```

**Token storage — the details that matter:**

| Property | Value | Assessment |
|---|---|---|
| Cookie name | `accessToken`, `refreshToken` | |
| `path` | `/` (set globally by `CookiesProvider`) | ✅ |
| `httpOnly` | ❌ **not set** | 🔴 **The token is readable by any JavaScript on the page.** A single XSS exfiltrates a full session. |
| `secure` | ❌ **not set** | 🔴 The token is sent over plain HTTP on any non-HTTPS origin. |
| `sameSite` | ❌ **not set** | Browser default is `Lax` in Chrome — mitigates most CSRF, but it is implicit, not deliberate. |
| `maxAge` / `expires` | ❌ **not set** | Session cookies — they die when the browser closes. (The refresh token therefore also dies, which limits the blast radius of #2.) |

**Because the cookie is not HttpOnly, the `react-cookie` `CookiesProvider` is
load-bearing:** `api.js` reads the token from `document.cookie` via `new Cookies()`.

### 11.2 Authorization

**There is no client-side authorization.** Specifically:

- ❌ **No route guards.** `/dashboard`, `/admin`, and `/onboarding` are all reachable
  without a token. They render (with mock data) and only fail when an API call is made.
- ❌ **No role checks.** The `role` prop on `DashboardLanding` only selects which nav
  arrays to render. Nothing prevents a user from navigating to `/admin` — and
  `/admin` is in the client route table, so it renders.
- ❌ **No conditional rendering on auth state.** Nothing reads the token to decide what
  to show.
- ✅ **Server-side authorization is presumed** — the API must reject an admin token on
  user endpoints and vice versa. The frontend cannot be relied upon for this.

**`auth.service.adminRegister(payload, adminSecret)`** sends an `x-admin-secret`
header. This is a **bootstrap credential** for creating the first admin. Because it is
sent as a header it will not appear in body-logging middleware, but it **will** appear
in a full request log. There is no caller for it in the UI.

### 11.3 Permission model

| Layer | Mechanism |
|---|---|
| API (authoritative) | Bearer token → user identity; server-side role checks. |
| Frontend (cosmetic) | Nav arrays selected by the `role` prop. Nothing enforced. |

### 11.4 Token contract fragility

> 🔴 **Stale / Broken** — the code demonstrably does something other than what it
> appears to. One of the two assumptions below is wrong.

Two token shapes are assumed in the same file:

```js
// src/api/api.js — refresh path
const response = await refreshTokenApi({ refreshToken: storedRefreshToken });
// refreshToken() already returned response.data, so:
const newAccessToken = response.data.access_token;   // ← body.data.access_token
//                                            ^^^^^^   double unwrap → ENVELOPED body
//                             ^^^^^^^^^^^ snake_case
```

```js
// src/landing/auth/Login.jsx — login path
setCookie("accessToken", response?.accessToken, cookieOptions);
//                       ^^^^^^^^^^^^^ camelCase, FLAT body
```

For both to work, `/auth/login` would have to return
`{ accessToken, refreshToken }` while `/auth/refresh` returns
`{ data: { access_token } }` — different casing *and* different envelope for the same
concept. **One of the two is wrong.** Symptoms:

| Which is wrong | Symptom |
|---|---|
| Login is wrong (`access_token` + envelope) | `accessToken` cookie is set to `undefined` → **every request goes out unauthenticated** → 401 on everything → the refresh path fires → also broken → the user is bounced to `/login` after one attempt. |
| Refresh is wrong (flat `access_token`) | `response.data.access_token` is `undefined` → `cookies.set("accessToken", undefined)` → the same unauthenticated-request cascade. |

**This is the single most likely cause of "the user logs in and immediately gets
kicked back to /login".** Verify against the backend before touching anything else.

### 11.5 Secrets management

| Secret | Where | Risk |
|---|---|---|
| Cloudinary API key + secret | `.env` (git-ignored, not tracked — verified via `git ls-files`) | 🔴 Would be **inlined into the public bundle** if referenced from client code. Currently unreferenced. Delete them. |
| JWTs | cookies (non-HttpOnly) | 🔴 XSS-readable. |
| Admin secret | passed as an argument to `auth.service.adminRegister` | 🔴 If ever called from the browser, it is public. **Must be server-side only.** |

**Positive notes:** the `.env` file is properly git-ignored and **is not tracked by
git** (`git ls-files` confirms). The git history contains a `Delete .env` commit
(`f7beed2`) — a secret was committed at some point and then removed. The history
still contains it.

### 11.6 Sensitive data handling

| Data | Handling | Issue |
|---|---|---|
| Password | Sent in the request body over HTTPS; never stored client-side; never logged (no `console.log` of the payload) | ✅ |
| JWT | Cookie (non-HttpOnly) | 🔴 XSS-readable. |
| Business description, brand kit | Sent to the API; **never persisted client-side** | ✅ (data loss, not leakage) |
| Cloudinary logo | Uploaded directly to Cloudinary, then the **public** `secure_url` is stored on the profile | ⚠️ The logo is publicly addressable. |
| Console logging | `console.log(response)` in `Login.jsx`, `Signup.jsx`, `Otp.jsx`; `console.log("new access token", response)` in `api.js` (logs the **entire refresh response**, which contains the new token!) | 🔴 **The refresh response — including the new access token — is logged to the browser console.** Remove it. |

### 11.7 Trust boundaries

```
┌──────────────────────────────────────────────────────────────────────┐
│ TRUSTED (same origin, our code)                                     │
│   index.html, /assets/*, main.jsx, all bundled JS                    │
├──────────────────────────────────────────────────────────────────────┤
│ SEMI-TRUSTED (same origin, user-controlled input)                    │
│   All form values → become API payloads                              │
│   ⚠ No output encoding strategy — React escapes by default ✅        │
├──────────────────────────────────────────────────────────────────────┤
│ UNTRUSTED (cross-origin)                                             │
│   api.ahiia.ai — responses are trusted and rendered directly         │
│   (React escapes text ✅, but `dangerouslySetInnerHTML` is never used │
│    anywhere — verify: no usage in the codebase ✅)                    │
│   api.cloudinary.com — returns `secure_url`, used in an <img src>    │
├──────────────────────────────────────────────────────────────────────┤
│ HOSTILE                                                            │
│   Nothing is fetched from a user-supplied URL.                       │
│   No `eval`, no `dangerouslySetInnerHTML`, no `innerHTML` with        │
│   user data (verify before adding).                                  │
└──────────────────────────────────────────────────────────────────────┘
```

**`dangerouslySetInnerHTML` — verified: not used anywhere in `src/`.** This is a
strong positive; preserve it.

### 11.8 Known risks (ranked)

| # | Risk | Severity | Mitigation |
|---|---|---|---|
| 1 | **Token refresh shape mismatch** ([§11.4](#114-token-contract-fragility)) | 🔴 Critical | Verify against the backend; standardise on one shape. |
| 2 | **No HttpOnly on auth cookies** | 🔴 High | Move tokens to HttpOnly cookies; use `withCredentials` + a server session, or at minimum set `secure: true, sameSite: "Lax"`. |
| 3 | **`console.log("new access token", response)`** leaks the token to the console | 🔴 High | Delete the log. |
| 4 | **No route guards** | 🟠 Medium | Add a `<RequireAuth>` wrapper reading the cookie. (The API must still enforce.) |
| 5 | **Cloudinary credentials in `.env`** | 🟠 Medium | Delete `VITE_CLOUDINARY_API_KEY` / `_SECRET`. |
| 6 | **Unsigned upload preset** = public write access to the media account | 🟠 Medium | Restrict the preset (allowed formats / max size) or proxy uploads. |
| 7 | **Refresh stampede** ([§5.4](#54-tier-4--transport-events-the-cross-cutting-pipeline)) | 🟠 Medium | De-duplicate concurrent refreshes. |
| 8 | **A secret was committed in git history** (commit `f7beed2` deleted `.env`) | 🟠 Medium | Rotate the credential; consider purging history. |
| 9 | **No CSP / security headers** | 🟡 Low | Configure headers in `vercel.json` (Vercel supports `headers`). |
| 10 | **No rate limiting / lockout on the client** (server-side unknown) | 🟡 Low | Server concern. |
| 11 | `email` type inputs are the only format validation; the server must re-validate | 🟡 Low | Server concern. |
| 12 | **`/admin` is client-routable and its nav links are visible** to any user | 🟡 Low | The API must 403. Optionally hide admin nav based on the user's role from `/user/me`. |

## 12. Error Handling Strategy

### 12.1 Error categories and where they are handled

| Category | Detection | Handling | User feedback |
|---|---|---|---|
| **Validation (4xx, 400)** | Server response | Component `catch` | `toast.error(error.response?.data?.message)` — **but only `Signup.jsx` and `Onboarding.jsx` read the server message.** `Login.jsx` and `Otp.jsx` show `error.message` (raw axios text like *"Request failed with status code 401"*). |
| **Unauthenticated (401, magic detail)** | `error.response.data.detail === "Invalid or expired token"` | **axios response interceptor** | Silent refresh + retry; on failure → toast + cookie wipe + hard redirect to `/login`. |
| **Unauthenticated (401, any other detail)** | Not detected by the interceptor | Falls through to the caller | Raw error toast. **The user stays on the page with a broken session.** |
| **Forbidden (403)** | Server response | Component `catch` (if any) | Usually none — the dashboard pages have no API calls. |
| **Conflict (409)** | `err.response.status === 409` | `Onboarding` step 2 fallback → per-field PATCH | Silent. |
| **Not found (404)** | Server response | Component `catch` | Usually `error.message`. |
| **Server error (5xx)** | Server response | Component `catch` | ⚠️ **Often swallowed entirely** (`console.log` only) — `Onboarding` step 2 and step 5. |
| **Network / CORS** | `error.response` is `undefined` | Component `catch` | `error.message` = *"Network Error"*. |
| **Timeout (60 s)** | axios `ECONNABORTED` | Component `catch` | *"timeout of 60000ms exceeded"*. No retry. |
| **Render error** | React throws during render | ❌ **No error boundary** | 🔴 **The entire app blanks to a white screen.** |
| **Unhandled promise rejection** | e.g. `Otp.jsx`'s unawaited `resendOtp` | Browser console only | The user sees a success toast for a failed request. |

### 12.2 Logging standards

**There is no logging standard.** The codebase uses bare `console.log`/`console.error`:

| Location | What is logged | Risk |
|---|---|---|
| `api.js:44` | `console.log("new access token", response)` | 🔴 **Logs the new access token.** |

| `Login.jsx:43` | `console.log(response)` | 🟠 Logs the login response (tokens). |

### 12.5 Render errors

**There is no `ErrorBoundary` anywhere in the app.** A thrown error during render
unmounts the whole React tree and the user sees a blank page. This is a real risk
because several components do work during render that can throw:

| Component | Render-time throw risk |
|---|---|
| `Onboarding.jsx` | `SIDEBAR_DATA[step]` — safe only because `step` ∈ 1..6. |
| `Onboarding.jsx` | `INDUSTRY_CATEGORIES.find(...)` — safe (array literal). |
| `Documents.jsx` | `STATUS_STYLES[doc.status]` — **`undefined` for an unknown status** → `className={undefined}` is fine, but a missing key throws. |
| `Overview.jsx` | `getStatusBadge(status)` has a `default` branch → safe. |
| `DocumentSetup.jsx` | `registryEntry.getCompletedSections(formData)` → throws if a form's completion function assumes a field type (e.g. `SOPForm`'s `s.trim()` on a non-string). |
| `SetupSidebar.jsx` | `completedCount / requiredSections.length` → **`NaN` if `requiredSections` is empty** → `width: "NaN%"` (harmless, but a symptom). |

**Recommendation:** add a top-level `ErrorBoundary` around `<App/>` in `main.jsx`.

### 12.6 Failure resolution paths per major failure type

| Failure | Cause | Detection | Resolution |
|---|---|---|---|
| **User cannot log in / is bounced back** | Token-shape mismatch ([§11.4](#114-token-contract-fragility)); or the API rejects the credentials; or the `accessToken` cookie was never written | Network tab → the login response body shape; `cookies` in DevTools → Application → Cookies | Compare the login response shape with `response?.accessToken`; check `document.cookie` after login. |
| **User sees "Session expired" repeatedly** | The refresh endpoint's response shape differs from `body.data.access_token`; or the refresh token was rotated server-side; or the `detail` string changed | Console: `new access token` log; Network tab: the 401 body | Verify the exact `detail` string and the refresh response envelope. |
| **All requests 404** | Trailing space in `VITE_API_URL`; or a wrong base URL | Network tab: the request URL | Strip the whitespace; rebuild. |
| **CORS error** | The API doesn't allow the origin or the `Authorization` header | Console: the CORS message | Server-side `CORSMiddleware` config. |
| **First request hangs ~60 s** | Render cold start | Network tab: the request is pending | Expected. Do not lower the timeout below ~60 s. |
| **Onboarding appears to skip / loses data** | Silent swallow of a failed `profile.create` / `brandKit.update` | Network tab shows a 4xx/5xx that the UI ignored | Fix the API or add error toasts. |
| **Logo upload fails silently** | Missing/invalid Cloudinary env | Network tab: the request to `api.cloudinary.com` | Check `VITE_CLOUDINARY_CLOUD_NAME` / `_UPLOAD_PRESET`. |
| **Blank white page** | A render error with no error boundary | Browser console: the React error | Read the console stack; add an error boundary. |
| **"Review & Generate" never enables** | `completedKeys.length !== requiredSections.length` — most likely the `MarketingPlanForm` `audienceMode` bug ([§14.2](#142-the-completion-contract--the-single-most-important-rule-set)) | Log `getCompletedSections(formData)` | Fix the comparison in `MarketingPlanForm`. |
| **404 after a page refresh on a deep link** | The Vercel rewrite is missing/misconfigured | Network tab: the document request | `vercel.json` must contain the rewrite rule. |
| **Document list is empty / always the mock 7 items** | `Documents.jsx` uses a hard-coded array | Read the component | Wire `getDocuments()`. |

|---|---|---|---|---|

### 13.3 Reading the console: an interpretation guide

The console is the primary telemetry channel. These are the lines you will see and
what each one means.

| Log line | Source | Interpretation |
|---|---|---|
| `new access token {…}` | `api.js:44` | A 401 with `detail === "Invalid or expired token"` occurred and the refresh succeeded. **The logged object contains the new access token — treat it as a secret.** |
| `{…}` (an axios error object) | `Onboarding.jsx` catches, `Login.jsx:57`, `Otp.jsx:92,115` | A request failed. The object's `response.status` and `response.data` tell you what actually happened; the `message` field is often just axios boilerplate. |
| `Failed to save {cardId}:` | `Onboarding.jsx:757` | One of the four AI-profile card PATCHes failed. The wizard will toast "Some fields could not be saved" and **will not advance to step 5**. |
| `waitlist signup: {email}` | `WaitListCta.jsx:10` | The waitlist form did **not** call the API. No data left the browser. |
| `send reset link to: {email}` | `ForgotPassword.jsx:25` | The forgot-password form did **not** call the API. |
| `undefined` | `api.js:53` | The refresh call failed and the response had no `data.message`. The session was terminated anyway. |
| (nothing) | `Onboarding.jsx:692`, `:778` | A 5xx occurred during profile creation or brand-kit save and was swallowed. **Check the Network tab — the console will not tell you.** |

### 13.4 Metrics

**There are no metrics.** The closest things to a measurement are:

- the axios `timeout: 60000` — the only numeric tuning constant in the transport;
- the `Analytics.jsx` chart widths, which animate from hard-coded percentages
  (`Analytics.jsx:99`), not from data;
- the admin dashboard's "System Uptime 99.98%" and "AI usage" tiles — **hard-coded
  string literals in JSX**, not API data.

> ⚠️ The admin Overview looks like a monitoring console but is entirely fictional.
> Anyone reading it as a health signal is reading a design mock-up.

### 13.5 Tracing

There is no request ID, no trace ID, no correlation ID, and no user identity
attached to an outbound request. The only per-request state the transport layer
maintains is the boolean `_retry` on the axios `config` object, which exists
purely to break the refresh/replay loop.

The closest thing to a trace is the fact that the response interceptor **replays
the same `config` object** (`api(originalRequest)` at `api.js:51`). Practical
consequence: in the Network tab, a refreshed request appears as a **second
identical request**, and the original request's `Authorization` header in the
Network tab may show the *old* token even though the *replayed* one carries the
new token.

### 13.6 Error reporting

None. A render error is caught by nothing, propagates to the React root, and
unmounts the entire tree — the user sees a white page and the only evidence is a
red stack trace in the console that most users will never open or report.

### 13.7 The DevTools stack is the real observability platform

Because nothing is instrumented, **every** diagnosis in this project starts in
the browser. The specific panels that matter:

| Panel | Use it for |
|---|---|
| **Network → Fetch/XHR** | Every request. Filter by `accessToken`/`refresh` to isolate the auth cycle. Check *Status*, *Timing*, *Response* body shape, and the `Authorization` request header. |
| **Network → request → Headers** | Confirm the `Authorization: Bearer …` header is present (or absent). |
| **Network → request → Timing** | Distinguish a 60 s timeout (`api.js:9`) from a genuinely slow server. |
| **Application → Cookies** | The only client-side persistence. Verify `accessToken`, `refreshToken`, `userData` and their values. |
| **Application → Local Storage / Session Storage** | **Always empty.** Nothing in this app persists client-side. If a feature "remembers" something, it is React state or a cookie. |
| **Console** | The `console.*` table in [§13.3](#133-reading-the-console-an-interpretation-guide). |
| **Sources → XHR breakpoints** | The single most powerful debugging tool for this codebase. Set a breakpoint on `XMLHttpRequest`/`fetch` to pause before every request leaves, and inspect the payload. |
| **Coverage** | Useful when hunting dead code ([§16.6](#166-dead-code)). |

### 13.9 Minimum viable observability (ordered, if you need to add any)

This is the smallest change set that makes the app debuggable in production.
Each step is independently valuable.

1. **Delete the credential logs.** Remove `api.js:44` and `Login.jsx:43`. (5 min,
   highest value.)
2. **Add an `ErrorBoundary` around `<App/>` in `main.jsx`.** (30 min, converts a
   white screen into a recoverable message.)
3. **Introduce `src/utils/logger.js`** with `logger.error/warn/info` that
   prefixes a timestamp and, in dev only, the component/context. Replace all 15
   `console.log` call sites. (1 hour, mechanical.)
4. **Propagate errors instead of swallowing them.** Replace the bare
   `catch (error) { console.log(error) }` blocks in `Onboarding.jsx` with toasts
   so the failure is visible to the user *and* the developer. (1 hour.)
5. **Add a request ID.** Generate `crypto.randomUUID()` in the axios request
   interceptor, set `config.headers['X-Request-Id']`, and log it with every
   error. (30 min, unlocks server-side correlation.)
6. **Add an error-reporting service** (Sentry's browser SDK is the cheapest
   option) with source maps uploaded per release. (2–4 hours + CI work.)
7. **Add `web-vitals` reporting** to a single endpoint, if performance matters
   to the product.

> Do **not** skip to step 6 before doing steps 1–2. Steps 1–2 are cheap and
> remove most of the "nothing happened" class of bug reports.

### 14.2 The completion contract — the single most important rule set

This is where the highest ratio of "it looks finished but isn't" bugs live.

**The contract has two halves that must agree:**

```
TEMPLATES[t].requiredSections[].key   ←  the SET of section keys the UI shows
        ═══════════════════════════════════════════════════════════════
getCompletedSections(data)[]           ←  the KEYS the form considers complete
```

A section key that appears in `requiredSections` but is never pushed by
`getCompletedSections` **can never be marked complete**, and the "Review &
Generate" button stays disabled forever.

**How the gate is computed (two independent implementations):**

| Location | Formula | Consequence |
|---|---|---|
| `DocumentSetup.jsx:54` | `completedKeys.length === template.requiredSections.length` | **Counts keys**, does not check they are the *right* keys. If `getCompletedSections` returns a duplicate or a foreign key, the count can equal the total while a real section is still empty. |
| `SetupSidebar.jsx:20-22` | `requiredSections.filter(s => completedKeys.includes(s.key)).length` | **Intersects** — always correct. |

> 🔴 These two counters can disagree. The footer (which gates the button) uses
> the count-based version; the sidebar progress bar uses the intersection-based
> version. A user can see "1 of 1 required sections complete" in the sidebar
> while the footer button is disabled.

### 14.3 Required-key contract per document type (✅ Verified)

Read directly from each form's `getCompletedSections`.

| Document type | `templateId` | Required section key | Completes when |
|---|---|---|---|
| Business Proposal | `business-proposal` | `executiveSummary` | `clientName && clientNeed` |
| | | `scopeOfWork` | `projectService && proposedSolution` |
| | | `pricing` | `items?.some(i => i.item && i.amount)` |
| | | `timeline` | `projectDuration` |
| Pitch Deck | `pitch-deck` | `documentBrief` | `purpose && problem` |
| SOP | `sop` | `theProcess` | `processName && performer && purpose && when && steps?.some(s => s.trim())` |
| Contract | `contract` | `otherParty` | `partyName && partyDetails` |
| | | `theAgreement` | `agreementAbout && provide && otherProvide && startDate && endDate` |
| Marketing Plan | `marketing-plan` | `whatYouAreMarketing` | `product && campaignDuration && hasAudience` |
| Business Plan | `business-plan` | `documentBrief` | `briefType && goal` |
| | | `financialInformation` | `otherFinancial \|\| revenueTarget \|\| fundingRequired` |

**Notes on individual rules:**

- `pricing` uses `.some(...)` — **one** priced line item is enough, even though
  the form renders three blank item rows.
- `theProcess` uses `steps?.some(s => s.trim())` — one non-blank step is enough.
  ⚠️ This will **throw** if a step is not a string (`s.trim is not a function`).
  It is currently safe because every step is created by `updateStep`/`addStep`
  as a string.
- `financialInformation` uses **OR**, not AND: any one of the three fields
  satisfies it.
- `hasAudience` in the Marketing Plan is the source of a live bug — see
  [§14.4](#144-worked-example-the-audiencemode-trap).

### 14.4 Worked example: the `audienceMode` trap

This is the canonical example of how a display default and a completion rule can
disagree. Read it before touching any form.

```
MarketingPlanForm.jsx:53   const audienceMode = data.audienceMode || "existing";
                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                            DISPLAY default: "existing"  → the "Use existing
                            audience" radio renders as SELECTED on first paint.

MarketingPlanForm.jsx:35   const hasAudience =
                              data.audienceMode === "existing" || ...
                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                            COMPLETION rule: reads data.audienceMode, which is
                            undefined until the user CLICKS the button.
```

**Consequence:** the UI shows the audience as chosen, the section stays
incomplete, the sidebar says "0 of 1 required sections complete", and the
"Review & Generate" button is permanently disabled — until the user clicks the
*already-selected-looking* radio button, which writes `audienceMode: "existing"`
into `formData`.

**Rule to remember:** *a UI default that is not written into state is not a
default.* If a rule depends on a field, the field must be initialised in the
state that the rule reads.

### 14.8 The onboarding step machine

`Onboarding.jsx` is a **client-side wizard with 6 steps**. `step` is a plain
`useState` number. There is no server-side session, no step validation, and no
way to resume — **reloading the page restarts at step 1**.

| Step | Screen | Exit handler | What it persists |
|---|---|---|---|
| 1 | Business basics (company name, industry, description, logo) | → 2 | Nothing yet |
| 2 | Review basics | `submitStep2` (`:664`) | `POST /api/v1/profile`; on 400/409 → per-field `PATCH /api/v1/profile/{field}` |
| 3 | AI inputs (offer, audience, advantage) | `submitStep3` (`:702`) | `POST /api/v1/profile/ai-complete`; on failure → locally generated default text |
| 4 | Four AI cards (mission, vision, advantage, audience) | `submitStep4` (`:743`) | `PATCH /api/v1/profile/{field}` ×4 with `action` |
| 5 | Brand kit (colors, font, tagline) | `submitStep5` (`:773`) | `PUT /api/v1/brand-kit` |
| 6 | Completion | — | Nothing |

**Legal transitions:**

```
1 ──▶ 2 ──▶ 3 ──▶ 4 ──▶ 5 ──▶ 6
        ▲                          │
        └──────────────────────────┘  (sidebar jump buttons: :1750 setStep(2),
                                       :1795 setStep(5), :1821 setStep(6))
```

**Rules:**

- Step 2 **always advances to step 3**, even if both the create *and* the
  per-field fallback failed (the `finally` block at `:696-699` unconditionally
  calls `setStep(3)`). 🔴 **Data loss is silent.** The user believes their
  company profile was saved; it may not exist server-side.
- Step 3 **always advances to step 4** (`:729-732`), substituting locally
  generated defaults if the AI call failed. ⚠️ The user may later "Accept"
  default text and persist it as if it were AI-generated.
- Step 4 advances to step 5 **only if all four card saves succeeded**; otherwise
  it toasts *"Some fields could not be saved"* and stays. ✅ This is the one
  step that behaves correctly.
- Step 5 **always advances to step 6** (`:780-783`) even if the brand-kit save
  failed. 🔴 Silent.
- The back button (`setStep(s => s - 1)`, `:1729`) can move backwards at any
  time; the forward direction is only through the submit handlers.

### 14.9 The AI-card lifecycle rules

Four cards, each mapped to a backend field name:

| Card id | Backend field | `CARD_FIELD_MAP` entry |
|---|---|---|
| `mission` | `mission` | `Onboarding.jsx:737` |
| `vision` | `vision` | `Onboarding.jsx:738` |
| `advantage` | `competitiveAdvantage` | `Onboarding.jsx:739` |
| `audience` | `targetAudience` | `Onboarding.jsx:740` |

**The `action` contract:** each card carries `action ∈ {"Accept", "Edit",
"Regenerate"}` (`:476`, `:484`, `:492`, `:500`) and that exact string is sent as
the `action` field of the PATCH body (`profile.service.js:20-26` →
`{ action, value }`).

**The action transitions:**

| From | User action | Resulting `action` | Line |
|---|---|---|---|
| any | click card body | toggles `isAccepted`; sets `action: "Accept"` | `:634` |
| any | click "Accept all" | sets all cards to `isAccepted: true`, `action: "Accept"` | `:640` |
| any | start editing | `action: c.isEditing ? "Edit" : c.action` | `:625` |
| any | click Regenerate | `action: "Regenerate"` with new content | `:656` |

**Rules:**
- 🔴 The action string is **case-sensitive** and must be exactly `Accept`,
  `Edit`, or `Regenerate`. The comment at `:754` says so explicitly. Any
  refactor that lowercases it, or that sends `"accept"`, will silently fail
  server-side validation.
- Cards with **empty content are skipped** (`:750`) — no PATCH is sent.
- A card is only sent if `CARD_FIELD_MAP[card.id]` exists. A new card id
  without a map entry is **silently ignored**.
- The four PATCHes are sent **sequentially** in a `for` loop (`:748`), not in
  parallel. The total latency is the sum of four round-trips.

### 14.10 Profile-persistence rules

```
submitStep2:
  POST /api/v1/profile  { companyName, industry, description, logoUrl? }
        │
        ├─ 2xx ─────────────────────────▶ advance to step 3
        │
        └─ 400 or 409
             └─▶ for each of companyName, industry, description, (logoUrl):
                    PATCH /api/v1/profile/{field}
                      body: { action: "update", value: <field value> }
                 via Promise.allSettled  ← failures are IGNORED
                    │
                    └─▶ advance to step 3 regardless
```

**Rules:**
- The fallback triggers **only** on HTTP 400 or 409. A 500, a 403, a network
  error, or a timeout does **not** trigger it — the profile is simply not saved.
- `Promise.allSettled` means **partial success is possible and invisible**: the
  company name may be saved while the description is not.
- 🔴 **There is no verification.** The wizard never re-reads the profile. Use
  `GET /api/v1/profile` to check what actually persisted.

```json
{
  "primaryColor": "string",
  "secondaryColor": "string",
  "font": "string",
```

### 14.12 Auth and session rules

| Rule | Where | Consequence if broken |
|---|---|---|
| The access token is read from the **`accessToken` cookie** on every request | `api.js:16-23` | No cookie → no `Authorization` header → 401. |
| The token is **camelCase `accessToken`** when set by `Login.jsx` | `Login.jsx:48` | 🔴 Must match the backend's response field exactly. See [§11.4](#114-token-contract-fragility). |
| The refresh response is read as **`response.data.access_token`** (enveloped + snake_case) | `api.js:43` | 🔴 Must match the backend's refresh envelope exactly. |
| The interceptor triggers **only** on `detail === "Invalid or expired token"` (exact string) | `api.js:31` | Any other 401 detail → no refresh, no replay. |
| A request is retried **at most once** | `api.js:32-34` | Prevents infinite loops; also means a genuinely-expired token fails on the replay. |
| On refresh failure the app **wipes 3 cookies and hard-redirects** to `/login` | `api.js:59-62` | Uses `window.location.href`, a **full page reload** — all in-memory state is lost, including the onboarding wizard. |
| `logout()` always redirects to `/login` | `auth.service.js:29-36` | The `finally` block guarantees the redirect even if the API call fails. |
| `isNewUser` is passed via **router state** (`location.state`) | `Login.jsx:25`, `Otp.jsx:113` | ⚠️ Router state does not survive a page refresh. If the user refreshes `/login`, `isNewUser` is lost and a brand-new user is sent to `/dashboard` instead of `/onboarding`. |

These are assumed, not verified — the server is not in this repo. Treat them as
a contract to confirm:

- Email uniqueness, password policy, OTP expiry and rate limits.
- Whether `POST /api/v1/profile` is idempotent (it is called on every step-2
  submit, so idempotency matters).
- Whether `PATCH /api/v1/profile/{field}` accepts `action: "update"` in
  addition to `Accept`/`Edit`/`Regenerate`.
- Whether `PUT /api/v1/brand-kit` is a full replace or a partial update.
- Authorization on every `/api/v1/*` route, including `/api/v1/admin/*`.
- AI generation behaviour, token costs, and rate limits.
- The `GET /api/v1/documents` list shape that `Documents.jsx` will need.

### 14.15 The industry CSV contract

The onboarding wizard lets the user pick **multiple sub-industries**, but the
backend receives **one flat string**.

```
User picks:  [Software Development]  [FinTech]
                    │
                    ▼  Onboarding.jsx:569
   selectedIndustries.join(", ")   →   "Software Development, FinTech"
                    │
                    ▼  POST /api/v1/profile
              industry: "Software Development, FinTech"      ← a single string
                    │
                    ▼  server stores one text column
              the client later splits on ","   (fuzzy matching)
```

**Rules:**
- ⚠️ The join separator is `", "` — a comma **and a space**. Any consumer that
  splits on `","` without trimming will get `" FinTech"` with a leading space.
- The delimiter is not escaped. A sub-industry containing a comma would corrupt
  the field.
- The contract is a **stringly-typed list**, not an array or a join table. It
  avoids a schema change at the cost of fuzzy matching, which means the server
  cannot reliably query "all users in FinTech" without a `LIKE`/`split_part`
  query.
- This is a **client-side serialization format**, and it is duplicated
  implicitly: the client joins with `", "` and any future reader must guess the
  same separator. There is no shared constant for it.

> 🔴 **If you change the join separator, you must change the server's
> splitter.** There is no version marker on the field. Treat the format as
> frozen once profiles exist in production.

### 15.2 The one historical fact that explains most of the codebase

**The API contract was designed against the auth screens, then ~20 dashboard
screens were built against a *hypothetical* contract and never reconciled.**

```
Aug 18 ──► Sep 01        Sep 11 ──► Sep 22        today
Auth screens        Dashboard screens       still unreconciled
+ onboarding        built MOCK-first
WIRED FIRST         API never wired
       ╲                        ╱
        ╲______________________╱
         the gap that IS this codebase
```

Consequences that follow directly from that ordering:

1. The auth screens define the token contract — and they define it
   **inconsistently** with each other ([§11.4](#114-token-contract-fragility)).
2. The dashboard screens were designed **without** a working reference, so their
   data shapes are guesses. `BrandKit.jsx` invents `socialLinks` as an array;
   the backend comment says string. `Documents.jsx` invents a 7-item mock.
3. **The mock-first approach means the UI is ahead of the API.** Any agent
   asked to "wire it up" must discover the real contract independently — the
   UI cannot be trusted as a specification.
4. The `/api/v1/documents/*` endpoint family in `endpoints.js` (20 endpoints,
   including revisions, guidance, assistant-action, export) has **no UI at
   all**. That is a backend-first, UI-later design that was never executed.

### 15.3 Decision: one axios instance with a global interceptor (`src/api/api.js`)

**Chosen:** a single `axios.create()` instance exported as `api`, with a request
interceptor that attaches the bearer token and a response interceptor that
handles token refresh and replay.

**Why it is right:** every caller gets auth and refresh for free. Adding a new
API call requires **zero** auth code. The refresh/replay logic exists in exactly
one place.

**Why it is fragile:**
- The refresh trigger is an **exact string match** on `detail` (`api.js:31`). A
  backend wording change silently disables the entire refresh mechanism.
- The interceptor has **no way to report** a refresh failure other than a toast
  and a hard redirect — and the hard redirect (`window.location.href`) discards
  in-memory state.
- It imports `auth.service.js`, which imports `api.js` back → **circular
  import** (see [§9.3](#93-the-circular-import-between-api-and-services)). It
  works only because of function hoisting.
- Because `services/*.js` all `return response.data`, the *response envelope*
  is stripped once — and `api.js:43` then reads `response.data.access_token`,
  i.e. it expects the envelope a *second* time. This double-unwrap is the
  root cause of the token-shape conflict.

### 15.4 Decision: cookies as the only client-side token store

**Chosen:** `react-cookie`, keys `accessToken`, `refreshToken`, `userData`,
written by `Login.jsx` and read by the request interceptor.

**Why it is right:** the token is available synchronously to the interceptor
without an async store, and it survives a page refresh (unlike router state).

**Why it is wrong:**
- The cookies are **not** `HttpOnly` (impossible from JS — the JS must read the
  token), **not** `Secure`, and **not** `SameSite`. They are therefore exposed
  to XSS and to CSRF.
- `userData` is **removed** by the interceptor on session termination but
  **never written** by anything. Dead cookie.
- `Login.jsx` uses `useCookies(["accessToken","refreshToken"])` while
  `api.js` uses `new Cookies()` — two different APIs for the same store.
- Because the refresh path also runs through the `api` instance, **the refresh
  request itself carries the (expired) `Authorization` header**. Harmless
  today; a source of 401 loops if the backend ever rejects malformed headers.

### 15.5 Decision: a thin, uniform service layer (`src/services/*.js`)

**Chosen:** every service function is `async`, calls `api.<verb>(ENDPOINTS.X,
payload)`, and returns `response.data`.

**Why it is right:** it strips the axios envelope in exactly one place, gives
components a clean `await someService(payload)` API, and keeps `ENDPOINTS` in
one catalogue.

**Why it is a limitation:**
- There is **no error normalisation**. Components still receive raw axios
  errors and each one handles them differently (or not at all).
- There is **no validation** of payloads before they leave the browser.
- There is **no caching, no retry policy, no cancellation** at the service
  level.
- `src/services/index.js` is a barrel that re-exports everything — and **no
  file imports it.** It is dead code that exists to look like a clean package
  boundary. If you import from it, you create an import cycle with `api.js`.

### 15.6 Decision: template-driven document setup

This is the **best-engineered part of the codebase**, and the model other
features should copy.

```
documentTemplates.js ──► TEMPLATES[]           (what sections exist)
                          │
                          ├─ requiredSections[].key
                          └─ optionalSections[].key
                                   │
FormRegistery.js ──► FORM_REGISTRY[templateId]
                          ├─ Form                    (what to render)
                          └─ getCompletedSections    (when it's done)
                                   │
DocumentSetup.jsx ──► formData state ──► completedKeys ──► gate the button
```

**Why it is right:**
- Adding a document type means touching **three** files in a fixed pattern.
- The section key is the single join key between "what to show" and "when it's
  complete" — a genuinely good abstraction.
- The registry is a plain object, so a missing entry is a **render-time**
  `undefined` — and `DocumentSetup.jsx:35` handles that with a friendly
  "We couldn't find that document type" screen. That is a well-designed
  failure path.

**Why it is fragile:** the join key is a **string with no type checking**. A
typo in `getCompletedSections` (pushing `"executiveSummary"` when the template
wants `"execSummary"`) produces a section that can never complete, and **no
error is raised anywhere**.

### 15.7 Decision: no global state library

**Chosen:** React `useState` in the component that owns the data; a custom
`<Outlet context>` protocol for the two places that need cross-component
communication (`DashboardLanding` → page title; `SettingsLanding` → save
protocol).

**Why it is right:** for an app of this size, `useState` + `Outlet context` is
entirely adequate and keeps the dependency surface tiny.

**Why it hurts:** the settings save protocol is a **hand-rolled pub/sub**:

```
SettingsLanding                      AccountSettings
   │                                      │
   │  Outlet context={{ markDirty,        │
   │                   registerSave }}    │
   └──────────────────────────────────────▶│
                                          │ useEffect →
                                          │ registerSave(async () => { ... })
   ◀───────────────────────────────────────┘
   │  setSaveHandler(fn); setDirty(true)
   │
   │  handleSave() → await saveHandler()  →  setSaving(false), setDirty(false)
```

This works, but it is **implicit coupling with no type checking and no
documentation** — a child that forgets to call `registerSave` silently falls
back to a 700 ms fake save (`SettingsLanding.jsx:31`). See
[Appendix B](#appendix-b--implicit-coupling).

### 15.8 Decision: an endpoint catalogue with backwards-compatible aliases

`endpoints.js` defines ~55 constants, including deliberate duplicates:
`VERIFY_EMAIL` / `VERIFY_OTP`, `RESEND_VERIFICATION` / `RESEND_OTP`,
`PROFILE` / `CREATE_USER_PROFILE` / `GET_USER_PROFILE` / `UPDATE_USER_PROFILE`,
`DOCUMENTS` / `GET_DOCUMENTS` / `CREATE_DOCUMENT`,
`GET_ONE_DOCUMENT` / `DOCUMENT_BY_ID`, `BLUEPRINTS` / `BLUEPRINT_BY_TYPE`.

**Why it is right:** the aliases are self-documenting — a caller picks the name
that reads best at the call site (`createUserProfile` vs `CREATE_USER_PROFILE`).

**Why it is a liability:** **eight different constants point at the same URL.**
Nothing enforces that a `GET` uses a `GET_*` constant, so it is trivially easy
to `api.post(ENDPOINTS.DOCUMENTS, …)` and get a 405. Nothing documents which
constant is the canonical one.

### 15.9 Decision: onboarding as a client-side wizard over server-side AI

The AI content is generated **server-side** (`POST /api/v1/profile/ai-complete`),
but the **workflow** — six steps, accept/edit/regenerate per card, progress
navigation — is entirely client-side.

**Why it is right:** the wizard can be changed without a backend deploy, and
each card's accept/edit decision is persisted individually, which is exactly
the granularity a user wants.

**Why it hurts:**
- **No resumability.** The wizard lives in React state; a refresh restarts at
  step 1 and the user's input is gone.
- The per-card `action` vocabulary (`Accept`/`Edit`/`Regenerate`) is a **backend
  contract expressed as a client-side string literal**, with no enum, no
  constant, and no validation.
- The step machine's `finally`-block advancement (§14.8) means **silent data
  loss** on two of the six steps.

### 16.2 The token-shape conflict

The single highest-impact defect. Detailed in
[§11.4](#114-token-contract-fragility).

| Site | Reads | Shape assumed |
|---|---|---|
| `Login.jsx:48` | `response?.accessToken` | Flat body, camelCase |
| `api.js:43` | `response.data.access_token` | Enveloped body, snake_case |

**The same backend cannot satisfy both.** The likely symptom is *"logs in
successfully, then is immediately bounced to `/login`"* — because the cookie is
set to `undefined` (the login body is snake_case) and the interceptor then
sends `Bearer undefined`.

### 16.3 No error boundary

Any render-time throw unmounts the entire React tree. The user sees a white
page. There is no recovery UI, no error report, no fallback route.
[§12.5](#125-render-errors).

### 16.4 No tests of any kind

- **Zero test files.** No `*.test.*`, `*.spec.*`, `__tests__/`, or `e2e/`.
- **No test runner in `package.json`** — no Vitest, no Jest, no Playwright, no
  Cypress.
- **No test script** in `package.json`.
- **No CI configuration** (no `.github/workflows/`).

For a codebase whose whole value proposition is a multi-step form-completion
contract, the absence of tests means every change to `getCompletedSections` is
a manual, unverified edit. This is the highest-leverage gap to close.

## 17. Common Debugging Playbook

### 17.1 The 60-second triage

Before anything else, run this sequence. It eliminates most issues.

```
1. Open DevTools → Console.        Any red error?  → read it literally first.
2. Open DevTools → Network → Fetch/XHR, clear it, reproduce the action.
3. Did a request fire?
      NO  → the UI is mocked, or the handler is not wired (see §16.1).
      YES → go to 4.
4. What is the status?
      2xx → the backend worked. The bug is in the response handling.
      4xx → the server rejected it. Check the request payload vs the contract.
      5xx → server-side. Capture the request ID and escalate.
      (pending) → cold start. Wait up to 60 s (api.js:9).
      CORS error → origin not allowed, or the preflight failed.
5. Did the request carry an Authorization header?
      NO  → the accessToken cookie is missing. Go to §17.3.
6. Did the response body have the shape the caller expects?
      NO  → shape mismatch. Go to §17.3.
```

### 17.2 Environment and build failures

| Symptom | Likely cause | Fix |
|---|---|---|
| `Failed to resolve import "./x"` | Case-sensitivity or a missing file | Check the exact path and extension. Linux (Vercel) is case-sensitive; Windows is not. **A path that works on Windows can fail on Vercel.** |
| `import.meta.env.VITE_API_URL` is `undefined` | `.env` missing, or the file is not in the repo (it is git-ignored) | Create `.env` locally. On Vercel, set the variable in **Project Settings → Environment Variables**. |
| All requests 404 | `VITE_API_URL` has a **trailing space** (`"https://api.ahiia.ai "`) | Strip the whitespace and rebuild. Vite does not trim env values. |
| `npm run dev` fails immediately | `node_modules` out of sync | `rm -rf node_modules && npm install`. Check `package-lock.json` is present. |
| `npm run lint` fails | **Expected** — 73 pre-existing errors | Do not treat lint as a gate. See [§16.5](#165-npm-run-lint-fails). |
| Env var changes not picked up | Vite caches env | **Restart the dev server.** Env vars are read at startup only. |
| Blank page, no console error | A render error caught by React's overlay in production | Check `console` for the stack; in dev, React shows an overlay. |
| 404 on a deep link after refresh | SPA rewrite missing | `vercel.json` must contain the rewrite (see [§16.7](#167-missing-routes-links-that-go-nowhere)). |

### 17.3 Authentication and session failures

**This is the most common and most mis-diagnosed area in this codebase.**

| Symptom | Root cause | Diagnosis | Fix |
|---|---|---|---|
| **"Logged in successfully", then bounced to `/login`** | 🔴 Token-shape conflict — the cookie is set to `undefined` because the login body is snake_case but the code reads `accessToken` | DevTools → Application → Cookies → `accessToken`. If the value is the string `undefined` or empty, this is it. Compare the Network-tab **login response body** with `Login.jsx:48`. | Make `Login.jsx` and `api.js` read the **same** field. Confirm the real backend shape first, then change both. |
| **"Session expired" on every request** | The refresh response shape ≠ `body.data.access_token` | Console → look for `new access token`; if absent, the refresh call failed. Network tab → inspect the **refresh** response body. | Align `api.js:43` with the real refresh envelope. |
| **401 with no refresh attempt** | The server's `detail` string ≠ `"Invalid or expired token"` | Network tab → the 401 response body's `detail` field. | Either align the string, or broaden the interceptor to also match on `status === 401`. **Do not guess the string — read it.** |
| **Endless 401 loop** | The replayed request still carries the bad token | Network tab → you will see the **same URL twice**. | The interceptor sets `originalRequest.headers.Authorization` before replaying (`api.js:50`) — verify the refresh response actually contains a *different* token. |
| **Cookie present but no `Authorization` header** | The request was made with plain `fetch`, not the `api` instance | Network tab → Headers | Every API call must go through `api` from `src/api/api.js`. A raw `fetch` bypasses the interceptor entirely. |
| **User logged out "randomly"** | The interceptor's `finally` path fired: refresh failed → cookies wiped → `window.location.href = "/login"` | Console → the refresh error log; the toast text. | See "Session expired" above. Also note the hard redirect **loses all React state**. |
| **New user goes to `/dashboard` instead of `/onboarding`** | `location.state.isNewUser` was lost | The user refreshed the page between OTP verification and login. Router state is not persisted. | Persist the flag (a cookie or a query param) instead of router state. |
| **OTP "resent successfully" but no email arrives** | `resendOtp` is **not awaited** (`Otp.jsx:88`) — the try/catch never sees the rejection | Console → an unhandled promise rejection. | `await resendOtp(payload)`. |
| **Google button does nothing** | No `onClick` (`Login.jsx:236`) | — | Wire `googleAuth()` — but note `GOOGLE_AUTH` is a *credential exchange* endpoint, so it needs a Google ID token first. |
| **Forgot-password does nothing** | `ForgotPassword.jsx` never calls the API | Network tab → no request | Call `forgotPassword({ email })`. |

### 17.9 What to capture before escalating

If a bug must go to the backend team or to another engineer, capture **all** of
this in one message. Most escalations fail because the reporter sends only a
screenshot.

```
1. The exact route and the steps to reproduce.
2. The console output (all of it, including the red stack).
3. The Network-tab entry: URL, method, status, request payload,
   request headers (REDACT the Authorization value), response body.
4. The `document.cookie` contents (REDACT the token values — keep the
   key names and note whether the value is a plausible JWT or the literal
   string "undefined").
5. Whether it reproduces with a fresh login.
6. The commit SHA of the deployed build.
```

> 🔴 **Never paste a live access or refresh token into a ticket, a chat, or a
> commit.** Redact the value but keep the *shape* — "a JWT" versus
> `"undefined"` versus "empty" is the diagnostic that matters.

## 18. AI-Agent Guidance

This section is written specifically for an AI agent (or a new engineer) about
to modify this repository without a human in the loop.

### 18.1 Ground rules

1. **The service layer is the contract; the UI is largely a mock.** Never
   assume a dashboard screen talks to the API. Verify with a Network-tab
   check or a grep for an `api.` call. ([§16.1](#161-the-mockdashboard-gap--the-defining-limitation))
2. **The backend is not in this repository.** You cannot verify an API
   contract from this repo. When a contract matters, say so explicitly rather
   than inventing one.
3. **Never guess a payload shape.** Read the service function, the endpoint
   constant, the comments in the service file, and the consumer component. If
   they disagree, that disagreement is a finding — report it, do not silently
   pick one.
4. **Never guess a string constant that the backend compares.** The
   `detail === "Invalid or expired token"` check and the
   `action ∈ {Accept, Edit, Regenerate}` contract are exact-match contracts.
5. **A green screen is not proof.** The dashboard renders beautifully with
   fabricated data. Verify against the Network tab.
6. **Do not "fix" the lint errors wholesale.** 59 of the 73 are unused
   imports; 11 are `react-refresh` warnings that are **architecturally
   intentional**; 3 are real. Blindly "fixing" the `react-refresh` ones by
   moving exports will damage the design.
7. **Do not rename `FormRegistery.js`.** The typo is load-bearing in every
   import path. Renaming it is pure churn.
8. **Do not add a state library, a router library, or an HTTP library.** The
   project deliberately has none ([§15.7](#157-decision-no-global-state-library)).
   Adding one is an architectural decision, not a cleanup.

### 18.2 The invariants — never break these

| # | Invariant | Where it lives |

| 2 | A form's `templateId` key **must equal** its `TEMPLATES[].id`. | `FormRegistery.js` |
| 3 | The `action` string sent to `PATCH /api/v1/profile/{field}` must be exactly `Accept`, `Edit`, or `Regenerate`. | `Onboarding.jsx:476-500` |

| 6 | The refresh path may retry a request **at most once**. | `api.js:32-34` |
| 7 | Cookies are written with `{ path: "/" }` — and removed with the same path. | `Login.jsx:46`, `api.js:59-61` |
| 8 | `formData` and `optionalValues` are **separate** state objects. | `DocumentSetup.jsx:18-19` |
| 9 | `handleField(field, value)` is the only way form state changes. | `DocumentSetup.jsx:24-25` |

### 18.6 Procedure: wire a dashboard page to the API

The pattern is identical on every page. Follow it exactly.

```
STEP 1 — find the service function.
   e.g. Documents.jsx needs GET_DOCUMENTS → document.service.js already has
   `getDocuments()`. If it does not exist, add it to the right service file.

STEP 2 — add local state:
   const [data, setData] = useState(null);
   const [loading, setLoading] = useState(true);
   const [error, setError] = useState(null);

STEP 3 — fetch on mount:
   useEffect(() => {
     let cancelled = false;
     (async () => {
       try {
         const res = await getDocuments();
         if (!cancelled) setData(res);
       } catch (e) {
         if (!cancelled) setError(e);
       } finally {
         if (!cancelled) setLoading(false);
       }
     })();
     return () => { cancelled = true; };
   }, []);

STEP 4 — render three states: loading, error, data.
   DO NOT skip the error state. The current codebase's worst habit is a
   silent catch; do not copy it.

STEP 5 — delete the mock array and every `setTimeout`.

STEP 6 — check the response shape BEFORE writing the render code.
   Log it once, inspect it, then write the mapping. Do not guess.

STEP 7 — verify in the Network tab: the request fires, the status is 2xx, and
   the data on screen matches the response body.
```

### 18.7 Procedure: change the token/auth contract

**This is the highest-risk change in the repository.** The current state is
already broken ([§16.2](#162-the-token-shape-conflict)).

```
STEP 1 — determine the REAL contract. Do not infer it. Ask the backend team,
        or read the actual login/refresh response bodies from the Network tab.
        Record:
          login response   → where is the access token?  what is it called?
                            is the body flat or enveloped?
          refresh response → same questions

STEP 2 — write ONE canonical shape. E.g. "the token is at <path>".

STEP 3 — make BOTH readers use it:
          Login.jsx:48   (writes the cookie)
          api.js:43      (reads the refreshed token)
        Ideally by introducing a single helper, e.g.
          export const extractToken = (body) => body?.data?.access_token;
        and using it in both places. This eliminates the class of bug rather
        than fixing one instance of it.

STEP 4 — also verify the *names* the cookie is stored under match the names
        the interceptor reads ("accessToken", "refreshToken").

STEP 5 — test the full cycle:
          login → cookie set with a real JWT value (not "undefined")
                → an authenticated request carries Authorization
                → a 401 with the exact detail string triggers a refresh
                → the replayed request carries the NEW token
                → a failing refresh clears the cookies and redirects

STEP 6 — remove the credential console.logs while you are in there.
```

### 18.8 Impact-analysis cheat sheet

When asked "what breaks if I change X?", consult this table.

| Change | Ripple effect |
|---|---|
| A field name in `TEMPLATES[].requiredSections` | → `getCompletedSections` in the matching form → the section can never complete → "Review & Generate" stays disabled → the user cannot generate a document of that type. |
| A key in `FORM_REGISTRY` | → `DocumentSetup.jsx:16` → `registryEntry` becomes `undefined` → the page renders "We couldn't find that document type". |
| `ENDPOINTS.X` | → every service function using it → the affected screen's request URL. Aliases: 8 constants share 4 URLs. |
| The interceptor's refresh logic | → every authenticated request in the app → login, onboarding, and all future dashboard calls. |
| The `api` base URL / timeout | → every request. A too-short timeout breaks Render cold starts (the 60 s value exists for that reason). |
| `WRITING_STYLES` | → `SetupSidebar` (the list) **and** `DocumentSetup.jsx:60-65` (the modal label). Miss the second and the modal lies. |
| A field name in a form | → `getCompletedSections` in the same file → possibly the `TEMPLATES` label. |
| `SIDEBAR_DATA` in `Onboarding.jsx` | → the wizard's left rail. An out-of-range `step` → `SIDEBAR_DATA[step]` is `undefined` → a render crash → **a blank app** (no ErrorBoundary). |
| `CARD_FIELD_MAP` | → step 4's save loop. A missing entry silently skips that card. |
| The `action` string casing | → the backend's per-field validation → the card save fails → step 4 never advances. |

### 18.9 Things an agent must never do

| Never | Why |
|---|---|
| Never add `localStorage`/`sessionStorage` for auth state | The refresh mechanism depends on a cookie read by the interceptor. |
| Never store a token in `localStorage` | It is strictly worse than a cookie here: no way to scope it, and it is trivially readable by any XSS. |
| Never call `api.get` with a raw URL string | Bypasses `ENDPOINTS` and the reviewer's ability to audit URLs. |
| Never use `fetch` for an authenticated call | It bypasses the bearer-token interceptor and the refresh/replay logic. (`utils/cloudinary.js` is the deliberate exception — it is an unauthenticated third-party upload.) |
| Never change the `action` string casing | The backend compares exactly. |
| Never add a second `axios.create()` instance | It would have a different interceptor chain and no auth. |
| Never delete `src/services/index.js` **and** import from it | Nothing imports it today; if you import from it you create a cycle with `api.js`. |
| Never add a `react-refresh`-violating export to a form file without understanding the registry | `FORM_REGISTRY` and `getCompletedSections` are deliberately co-located with the form. |
| Never "clean up" the `React` default import in a file that uses `React.` explicitly | Some files use `React.Fragment` or `React.StrictMode`; check before removing. |
| Never assume a `setTimeout` mock is a bug to be removed casually | Some are intentional UX (chart animations). The *save* mocks are the ones to replace. |
| Never claim a fix works without checking the Network tab | The dashboard lies. |
| Never paste a token into a commit, a log, or a ticket. | Security. |
| Never add a secret to a `VITE_`-prefixed variable | Vite inlines it into the client bundle. |

### 18.10 Common agent mistakes, and the correction

| The mistake | Why it is wrong | The correction |
|---|---|---|
| "The dashboard is empty because the API isn't implemented" | The dashboard is **fully populated with mock data**. It is not empty; it is fake. | Wire the page to the service function. See [§18.6](#186-procedure-wire-a-dashboard-page-to-the-api). |
| "The API call returns `undefined` — the endpoint is missing" | The service returns `response.data`, so `undefined` means the *body* was undefined. Check the HTTP status. | Look at the status code and the raw body in the Network tab. |
| "I'll add a `try/catch` and show a toast" — everywhere | Correct instinct, but it will surface **many** pre-existing silent failures at once and change user-visible behaviour broadly. | Add error handling **only in the path you are changing**, unless the task is explicitly about error handling. |
| "I'll fix all 73 lint errors" | 11 are architecturally intentional; a mechanical "fix" damages the design. | Fix the 59 unused imports; **configure** ESLint for `react-refresh`; fix the 3 `set-state-in-effect` cases individually. |

| "The app has no persistence" — therefore I'll add `localStorage` | There *is* persistence: cookies, plus a full backend for the auth domain. | Use the cookies and the API. |
| "The onboarding wizard saves the profile" | It *tries*, and advances regardless of failure. | Verify with `GET /api/v1/profile`. |

## Appendix B — Implicit Coupling

Dependencies that are **not visible in the import graph** and that break silently
when broken.

### B.1 The completion contract (string-joined, untyped)

```
documentTemplates.js  TEMPLATES[].requiredSections[].key   ─┐
                                                            ├─ string equality ──┐
forms/XForm.jsx       getCompletedSections() → pushed keys   ─┘                  │
                                                                                 ▼
DocumentSetup.jsx:54   completedKeys.length === requiredSections.length
SetupSidebar.jsx:20   requiredSections.filter(s => completedKeys.includes(s.key))
```

**No import connects these.** A typo in either half produces a section that can
never complete, a permanently disabled button, and **zero error output**.

### B.2 The settings save protocol (`SettingsLanding` ⇄ its children)

```
SettingsLanding.jsx:113   <Outlet context={{ markDirty, registerSave }} />
        ▲                          │
        │  setSaveHandler(fn)      │  child calls useEffect(() => registerSave(fn), [])
        │  setDirty(true)          │  child calls markDirty() on every change
        └──────────────────────────┘
```

**Coupled but unenforced:**
- A child that never calls `registerSave` gets a **700 ms fake save** with a
  green "Saved" indicator — the user believes their change persisted.
- A child that calls `registerSave` on every render creates an infinite
  re-registration loop.
- A child that calls `markDirty` but not `registerSave` produces a Save button
  that does nothing real.
- `registerSave` stores exactly **one** handler — a last-writer-wins registry,
  not a collection. With multiple tabs mounted at once, only the last one wins.

### B.3 The header-title protocol (`DashboardLanding` → every page)

```
DashboardLanding.jsx:116   <Outlet context={{ setHeaderTitle }} />
```

- `DashboardHeader` receives `titleOverride={headerTitle}`.
- Any dashboard page can call `useOutletContext().setHeaderTitle("…")` to
  override the header title.
- 🔴 **Shadowing:** `SettingsLanding.jsx:113` renders its own `<Outlet context={{ markDirty, registerSave }} />`, which **replaces** the outer context. A settings child therefore **cannot** reach `setHeaderTitle` — the settings page's header title is never overridden.
- **Coupling to a React Router implementation detail:** the context shape is
  an implicit contract. Renaming `setHeaderTitle` breaks every consumer
  silently (`useOutletContext()` returns `undefined`, and
  `setHeaderTitle(...)` throws a `TypeError`).

### B.4 The three-way document-type binding

```
documentTemplates.js  TEMPLATES[].id            "pitch-deck"
FormRegistery.js     FORM_REGISTRY["pitch-deck"]
App.jsx              path="create-document/:templateId"   ← the URL segment
```

All three must agree. The URL segment is the *only* place the id enters the
system, and `DocumentSetup.jsx:15-16` looks it up in **both** maps. A mismatch
produces the friendly "We couldn't find that document type" screen — which
looks like a user error but is a config error.

### B.5 The token contract (`Login.jsx` ⇄ `api.js`)

```
Login.jsx:42   const response = await login(payload);        → response.data
Login.jsx:48   setCookie("accessToken", response?.accessToken, …)
                                  ^^^^^^^^^^^^^ camelCase, flat

api.js:43      const newAccessToken = response.data.access_token;
                                    ^^^^^^^^^^^^^^ snake_case, enveloped
```

Two files, one backend, **two incompatible assumptions**. Nothing in the
toolchain, the type system, or the lint config catches it.

### B.6 The circular import (`api.js` ⇄ `auth.service.js`)

```
api.js:4          import { refreshToken as refreshTokenApi } from "../services/auth.service";
auth.service.js:1 import { api } from "../api/api";
```

This works **only** because `refreshToken` is a `const` arrow function that is
*referenced* at call time (not at module-evaluation time). If the import order
flipped such that `api.js` evaluated `auth.service.js` while `auth.service.js`
was mid-evaluation, the binding would be in the temporal dead zone and the app
would throw `Cannot access 'refreshToken' before initialization`.

**Practical impact:** the module graph is fragile to reordering, and any
refactor that turns `refreshToken` into an eagerly-invoked value breaks it.

### B.7 Cloudinary bypasses the app's own transport

`utils/cloudinary.js` uses raw `fetch`, **not** the `api` instance. This is
correct (it is a third-party, unauthenticated upload) but it means:
- no timeout (a hung upload hangs forever);
- no error normalisation (it throws a plain `Error`);
- no retry;
- it is the **only** upload path — the dashboard's `BrandKit.jsx` and
  `CompanyProfile.jsx` "uploads" just store `file.name` and never upload at all.

### B.8 Internal coupling inside `Onboarding.jsx`

The file is 1 932 lines with **~20 pieces of state** and **5 submit handlers**
that all read and write the same state. Couplings worth knowing:

| Coupling | Detail |
|---|---|
| `submitStep2` → `submitStep3` | Step 2 must have written `companyName`, `industry`, `description` for step 3's AI prompt to be meaningful. Step 3 does **not** read them — it sends only `{ offer, audience, advantage }`. So the AI never sees the company name or industry it was just given. |
| `submitStep3` → `submitStep4` | Step 3's `catch` writes local default text into the cards via `updateCardContent`. Step 4 then persists those defaults with `action: "Accept"`. **Defaults can be persisted as if they were AI output.** |
| `submitStep4` → `submitStep5` | Step 4 requires **all four** cards to save before advancing. This is the only handler with a real success gate. |
| `selectedIndustries` → `industry` | An effect (`Onboarding.jsx:569`) derives the flat `industry` string. The chips and the string are two representations of one concept. |
| `isAccepted` vs `action` | Two parallel booleans/strings per card. `isAccepted` drives the UI; `action` drives the API. They can disagree (e.g. `action: "Regenerate"` while `isAccepted: true`). |
| `aiCards[0].content` | `submitStep3`'s catch reads `aiCards[0].content` **directly** from the render-scope closure rather than the updater — a stale-closure risk. |

### B.9 The signup → OTP → login chain

```
Signup.jsx:83   navigate("/otp", { state: { email } })
Otp.jsx:31      const email = location.state?.email        ← undefined on refresh
Otp.jsx:113     navigate("/login", { state: { isNewUser: true } })
```

Every hop uses **router state**, which is memory-only. There is no fallback

`SolarTech Nigeria` appears in **five** places with no shared source:

| Location | Form |
|---|---|
| `DashboardLanding.jsx:88-91` | `{ name: "Chidi Okafor", company: "SolarTech Nigeria", initials: "CO" }` |

## Appendix C — Non-Obvious Side Effects

Actions that happen as a consequence of something else, with no explicit call
site.

### C.1 The axios response interceptor has six side effects

Every single request that passes through `api` can, without any explicit code
at the call site:

| # | Side effect | Trigger | Location |
|---|---|---|---|
| 1 | Sets the `Authorization` header | Every request, if the cookie exists | `api.js:16-23` |
| 2 | **Re-issues the request** | 401 with the exact magic `detail` | `api.js:51` |
| 3 | **Writes the `accessToken` cookie** | A successful refresh | `api.js:47` |
| 4 | **Deletes three cookies** (`accessToken`, `refreshToken`, `userData`) | A failed refresh | `api.js:59-61` |
| 5 | **Performs a full page navigation** to `/login` | A failed refresh | `api.js:62` |
| 6 | **Shows a toast** | A failed refresh | `api.js:54-57` |

> 🔴 **Consequence for agents:** adding an API call means accepting all six.
> In particular, a 401 on *any* endpoint can silently terminate the user's
> session and wipe their wizard.

### C.2 `window.location.href` — full page reload

| Location | Trigger | Effect |
|---|---|---|
| `api.js:62` | Refresh failure | **Full reload.** All React state, all in-progress form data, and all router state are lost. |
| `auth.service.js:34` | Logout (even if the API call failed — it is in a `finally`) | Full reload to `/login`. |

### C.3 `ScrollToTop` — a global scroll side effect

`ScrollToTop.jsx` is mounted **outside** `<Routes>` in `App.jsx:32`, so **every
navigation** scrolls the window to `(0,0)`. This affects the landing page's
smooth-scroll sections too: clicking a header anchor that navigates will fight
the scroll.

### C.4 The onboarding wizard scrolls itself

`Onboarding.jsx:576-579` — on every `step` change, the content panel is
smooth-scrolled to the top **and** the industry dropdown is closed. If you add a
step, this effect fires for it too.

### C.5 `useScrollSpy` mutates the landing nav

`useScrollSpy.js:20` calls `setActiveId` from an `IntersectionObserver`
callback — a state update triggered by scrolling. The nav highlight is therefore
a **side effect of scrolling**, not of navigation.

### C.6 The `companyName` field is derived, not owned

`Onboarding.jsx:568-570` — `setIndustry(selectedIndustries.join(", "))` runs in
an effect. Toggling a sub-industry chip mutates `industry` **as a
consequence**. The `industry` state is downstream of `selectedIndustries`, and
writing to it directly would be overwritten.

### C.7 `console.log` writes to the user's console

Not a side effect anyone plans for, but real:

| Location | Leaks |
|---|---|
| `api.js:44` | 🔴 A live access token. |
| `Login.jsx:43` | 🔴 The full login response (both tokens). |

### C.9 The `Documents.jsx` navigation is a side effect of a click

`Documents.jsx` navigates to `/dashboard/documents/${doc.id}` — a route that
**does not exist**. React Router renders nothing for an unmatched path inside a
layout route, so the dashboard shell appears with an **empty content area**.

### C.10 The `GenerateModal` mount/unmount

`DocumentSetup.jsx:172-182` — the modal is conditionally rendered. Mounting it
resets its internal state (progress animation, disabled buttons). Because it
is unmounted rather than hidden, any state it holds is lost between openings.

### C.11 The document setup's `formData` is a single mutable-ish object

`handleField` merges a new key into `formData` (`DocumentSetup.jsx:24-25`).
Because `completedKeys` is memoised on `[registryEntry, formData]`, **every**
keystroke re-runs `getCompletedSections` — a cheap but real per-keystroke cost,
and the reason the progress bar animates on each character.
